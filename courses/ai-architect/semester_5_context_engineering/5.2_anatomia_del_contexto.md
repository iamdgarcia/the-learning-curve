# Anatomía del contexto: las cinco capas

**Semestre:** 5 — Context Engineering
**Lección:** 5.2
**Duración estimada:** 9-11 min
**Formato visual:** Excalidraw (stack vertical de 5 capas con propiedades anotadas)

---

## Objetivo de la lección

Al terminar esta lección, el alumno mapea cualquier sistema de IA real a las cinco capas del contexto, identifica cuántos tokens consume cada capa, y detecta cuál de ellas está causando problemas de calidad o coste.

---

## Guión

### Intro (25 seg)

Lección anterior definimos context engineering. Ahora vamos a abrirlo. El contexto que un LLM recibe no es un bloque monolítico de texto. Tiene estructura. Cinco capas con propiedades distintas, problemas distintos y decisiones de diseño distintas.

Entender cada capa es lo que te permite diagnosticar problemas en producción en lugar de adivinar.

---

### Bloque 1 — Capa 1: System prompt (2 min)

El system prompt es la capa más estable del contexto. Se establece una vez — en el código, no en la conversación — y define el comportamiento base del LLM: su rol, sus restricciones, el formato de sus respuestas, su tono.

Propiedades clave:
- **Quién lo controla:** el sistema, no el usuario.
- **Cuándo se actualiza:** raramente. Cambios en el system prompt son deployments, no configuración en runtime.
- **Consumo de tokens:** estático. Cada llamada paga por él. Si tu system prompt tiene 2000 tokens y haces 1M de llamadas al mes, eso son 2B tokens de input solo de overhead fijo.

El error más común con el system prompt es usarlo como vertedero de instrucciones. Cada instrucción que añades al system prompt compite por la atención del modelo con el resto. Los LLMs no leen el system prompt como un humano lee un manual — lo procesan como parte del contexto. Demasiadas instrucciones y algunas empiezan a ignorarse.

Regla práctica: el system prompt debe tener solo lo que es verdaderamente invariante. Lo que cambia según el usuario, la sesión o la tarea va en otras capas.

---

### Bloque 2 — Capa 2: Few-shot examples (1.5 min)

Los few-shot examples son pares input/output que le muestran al LLM exactamente cómo quieres que responda. No se lo explicas, se lo demuestras.

Propiedades clave:
- **Quién los controla:** el sistema. El usuario no los ve.
- **Cuándo se actualizan:** esporádicamente. Cuando el formato de output cambia o cuando el modelo empieza a derivar.
- **Consumo de tokens:** puede ser alto. Tres buenos ejemplos de input/output complejo consumen más tokens que el system prompt. Elige pocos ejemplos de alta calidad sobre muchos mediocres.

El impacto de los few-shots es desproporcionado. Un buen ejemplo vale más que dos párrafos de instrucciones. El modelo aprende el patrón de forma directa. Si el output que necesitas tiene estructura compleja — JSON anidado, formato específico, razonamiento en pasos — un ejemplo resuelve lo que la instrucción escrita lucha por comunicar.

El riesgo: un few-shot ejemplo con errores o con formato incorrecto introduce un patrón que el modelo puede seguir en producción.

---

### Bloque 3 — Capa 3: Retrieved documents (2 min)

Esta es la capa que más varía de llamada a llamada y la que tiene el mayor impacto en la calidad del output en sistemas con RAG.

Propiedades clave:
- **Quién la controla:** el sistema de retrieval. El pipeline decide qué documentos se inyectan.
- **Cuándo se actualiza:** en cada llamada. Es la capa dinámica por definición.
- **Consumo de tokens:** el más variable y potencialmente el más alto. Un sistema que recupera 10 chunks de 500 tokens cada uno añade 5000 tokens por llamada.

Los documentos recuperados le dan al LLM acceso a conocimiento específico, actualizado o propietario que no tiene en sus parámetros. Pero la calidad del retrieval determina la calidad del output: documentos irrelevantes o contradictorios degradan la respuesta aunque el resto del sistema sea perfecto.

Problema específico: **conflicto entre documentos y system prompt.** Si un documento recuperado contiene instrucciones o afirmaciones que contradicen el system prompt, el LLM tiene que arbitrar. A veces sigue los documentos. A veces sigue el system prompt. Raramente lo reporta explícitamente.

En la Lección 5.3 cubrimos RAG como estrategia completa. En la Lección 5.4 cubrimos chunking y reranking. Por ahora: esta capa existe, crece, y necesita gestión activa.

---

### Bloque 4 — Capa 4: Conversation history (2 min)

El historial de conversación es la capa que garantiza que el LLM tenga memoria dentro de una sesión. En la práctica: la lista de mensajes previos entre usuario y asistente que se incluye en cada llamada.

Propiedades clave:
- **Quién la controla:** el sistema gestiona qué se incluye; el usuario la genera.
- **Cuándo se actualiza:** en cada turno. Crece linealmente.
- **Consumo de tokens:** acumulativo. En conversaciones largas, el historial se convierte en el mayor consumidor de tokens del contexto.

El problema de fondo: los LLMs no tienen memoria entre llamadas. El historial es el mecanismo de ilusión de memoria. Cada llamada recibe todo el contexto relevante de nuevo. Si la conversación tiene 50 turnos, los primeros turnos compiten por la atención del modelo con los más recientes — y los más recientes suelen ganar. Los primeros turnos pueden efectivamente "desvanecerse" aunque estén técnicamente en el contexto.

Esto tiene implicaciones de diseño críticas: no puedes dejar que el historial crezca indefinidamente. La Lección 5.5 cubre estrategias de compresión. Por ahora: el historial es la primera fuente de context overflow y la primera cosa que recortas cuando el sistema se vuelve lento o caro.

---

### Bloque 5 — Capa 5: Tool results (1.5 min)

Los resultados de herramientas son los outputs de funciones externas que el LLM llamó durante su proceso de razonamiento: búsquedas web, consultas a bases de datos, resultados de APIs, ejecuciones de código.

Propiedades clave:
- **Quién los controla:** el sistema ejecuta las herramientas; el LLM las invoca.
- **Cuándo se actualizan:** on-demand, en cada iteración del agente.
- **Consumo de tokens:** impredecible. Un resultado de API puede ser 50 tokens o 50.000 tokens dependiendo de lo que devuelva.

El problema específico de esta capa: los resultados llegan en formato bruto. Una consulta SQL devuelve un CSV. Una API devuelve un JSON con campos que el LLM no necesita. Si inyectas el resultado bruto, estás llenando el contexto de ruido.

La práctica correcta: normalizar y truncar resultados de herramientas antes de inyectarlos. Extraer solo los campos relevantes. Resumir cuando el resultado es extenso. El LLM que recibe un resultado limpio de 200 tokens razona mejor que el que recibe el payload completo de 3000 tokens.

---

### Bloque 6 — El mapa de tokens: quién se lleva qué (1.5 min)

En un sistema de producción típico, la distribución de tokens de input por llamada es aproximadamente esta:

- System prompt: 5-15% (fijo, overhead constante)
- Few-shot examples: 10-25% (fijo o semi-fijo)
- Retrieved documents: 30-60% (variable, el mayor componente)
- Conversation history: 5-40% (crece con la sesión)
- Tool results: 0-30% (episódico)
- User prompt: 2-10% (lo que parece lo más importante y en realidad es la parte más pequeña)

Cuando el coste de una llamada sube, la primera pregunta no es "cómo optimizo el prompt del usuario." Es "qué capa está creciendo."

---

### Decisión de diseño (cierre, ~1 min)

La decisión que necesitas saber tomar después de esta lección: cuando algo falla en tu sistema, cómo aislar en qué capa está el problema.

Framework de diagnóstico: observa qué cambia entre una llamada que funciona y una que no. Si el system prompt y los few-shots son idénticos y el output varía, el problema está en los documentos recuperados, el historial o los resultados de herramientas.

Para diagnosticar sin ambigüedad: logea el contexto completo de cada llamada en desarrollo. No solo el prompt del usuario — el contexto serializado completo. Cuando ves un output incorrecto, la respuesta está en ese log.

En producción, instrumenta el tamaño de tokens por capa. Un dashboard que muestra distribución de tokens por llamada es más valioso que cualquier otro monitoring en un sistema de IA.
