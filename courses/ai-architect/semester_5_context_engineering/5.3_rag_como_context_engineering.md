# RAG como Context Engineering

**Semestre:** 5 — Context Engineering
**Lección:** 5.3
**Duración estimada:** 9-11 min
**Formato visual:** Excalidraw (pipeline RAG completo de izquierda a derecha, dos fases: ingest y query)

---

## Objetivo de la lección

Al terminar esta lección, el alumno diseña el pipeline RAG completo —desde ingestión hasta respuesta— y puede justificar por qué RAG domina sobre fine-tuning para conocimiento dinámico.

---

## Guión

### Intro (25 seg)

RAG es el acrónimo más usado en IA aplicada en los últimos dos años: Retrieval Augmented Generation. Hay mucho marketing alrededor. Vamos a limpiarlo.

RAG es, exactamente, una estrategia de context engineering. Recuperas solo el conocimiento relevante para la consulta actual y lo inyectas en la capa de retrieved documents del contexto. Eso es todo.

---

### Bloque 1 — Por qué RAG existe: el problema que resuelve (2 min)

Un LLM tiene conocimiento estático: lo que aprendió durante el entrenamiento hasta su fecha de corte. Si tu aplicación necesita conocimiento que cambia — documentación de producto actualizada, normativas vigentes, datos de clientes, bases de conocimiento internas — el LLM por sí solo no puede tenerlo.

Tienes tres opciones para darle conocimiento actualizado a un LLM:

**Opción 1: Meter todo en el contexto.** Para documentación pequeña funciona. Para una base de conocimiento de 10.000 documentos, no. No cabe en ninguna ventana de contexto y sería prohibitivamente caro.

**Opción 2: Fine-tuning.** Reentrenar el modelo con tus datos. Problemas: caro, lento, y el conocimiento sigue siendo estático — cada vez que actualizas la documentación, tienes que reentrenar. No escala.

**Opción 3: RAG.** Almacenas los documentos externamente. En cada consulta, recuperas solo los fragmentos relevantes y los inyectas en el contexto. El modelo accede al conocimiento correcto sin tenerlo en sus parámetros. Escala. Es actualizable. Es auditabie.

RAG gana para conocimiento dinámico, actualizable o propietario. Fine-tuning gana para cambiar el comportamiento, el estilo o las capacidades del modelo — no para darle conocimiento factual nuevo.

---

### Bloque 2 — El pipeline RAG: fase de ingestión (2.5 min)

El pipeline RAG tiene dos fases. La primera es la ingestión: procesar y almacenar los documentos fuente.

**Paso 1 — Document loading:** cargar los documentos desde sus fuentes. PDFs, páginas web, bases de datos, APIs, repositorios de código. Cada fuente tiene su parseo específico.

**Paso 2 — Chunking:** dividir los documentos en fragmentos. Los LLMs no procesan documentos completos de 50 páginas — procesan chunks. La estrategia de chunking determina la calidad del retrieval. (Lección 5.4 va aquí en detalle.)

**Paso 3 — Embedding:** convertir cada chunk en un vector numérico que captura su significado semántico. El modelo de embeddings (text-embedding-3-small, ada-002, etc.) produce un vector de alta dimensión — típicamente 768 a 3072 dimensiones — que representa el chunk en un espacio semántico.

Propiedad clave de los embeddings: chunks semánticamente similares producen vectores cercanos en ese espacio. "Cómo configurar autenticación" y "pasos para login de usuario" estarán cerca aunque no compartan palabras clave.

**Paso 4 — Storage:** almacenar los vectores en una base de datos vectorial. pgvector si ya usas PostgreSQL. Pinecone para escala masiva gestionada. Chroma o Qdrant para desarrollo y casos mid-size. Weaviate para casos con capacidades de búsqueda híbrida.

La fase de ingestión ocurre offline. Cuando subes documentos nuevos, ejecutas este pipeline. El retrieval en runtime solo usa lo ya almacenado.

---

### Bloque 3 — El pipeline RAG: fase de query (2 min)

La segunda fase es la query: lo que ocurre en runtime cuando llega una consulta del usuario.

**Paso 5 — Query embedding:** el texto del usuario se convierte en un vector con el mismo modelo de embeddings que usaste en la ingestión. Crítico: mismo modelo en ingestión y query. Vectores de modelos distintos no son comparables.

**Paso 6 — Similarity search:** buscas en la base de datos vectorial los chunks cuyo vector está más cerca del vector de la query. La métrica más común es cosine similarity. Recuperas los top-K chunks más similares — típicamente K entre 5 y 20.

**Paso 7 — Reranking (opcional pero recomendado):** los top-K chunks se reordenan con un modelo de reranking más preciso. El embedding model es rápido y generalista; el reranker es más lento pero más preciso para relevancia contextual. (Lección 5.4.)

**Paso 8 — Context injection:** los chunks seleccionados se inyectan en la capa de retrieved documents del contexto LLM. El prompt del sistema típicamente incluye instrucciones como "responde usando solo la información de los documentos proporcionados."

**Paso 9 — Generation:** el LLM genera la respuesta usando el contexto enriquecido.

---

### Bloque 4 — Bases de datos vectoriales: cuál elegir (1.5 min)

La elección depende de tres variables: escala, latencia requerida, y fricción operacional.

**pgvector:** extensión de PostgreSQL. Si ya tienes Postgres, añade búsqueda vectorial sin nueva infraestructura. Excelente hasta decenas de millones de vectores. La opción lazy y correcta para la mayoría de casos.

**Qdrant:** open source, Rust, muy rápido, excelente para búsqueda híbrida (semántica + keyword). Self-hosted o cloud managed. Buen balance entre performance y control.

**Pinecone:** fully managed, zero-ops, escala a miles de millones de vectores. Caro. Solo vale si el tamaño o el equipo justifican delegar completamente la operación.

**Chroma / LanceDB:** ideales para development, prototipos, y casos donde la simplicidad importa más que la escala.

Regla práctica: empieza con pgvector si ya tienes Postgres. Migra cuando tengas un motivo concreto medido.

---

### Bloque 5 — RAG vs fine-tuning: la decisión (1 min)

Esta es la pregunta que más se repite. La respuesta es más sencilla de lo que parece.

**Usa RAG cuando:** el conocimiento cambia, es grande, es propietario, necesitas citar fuentes, o necesitas que el sistema sea auditable.

**Usa fine-tuning cuando:** quieres cambiar el estilo de respuesta del modelo, enseñarle un formato muy específico, o adaptar sus capacidades a un dominio con vocabulario muy especializado donde los embeddings pre-entrenados fallan.

En la práctica: la mayoría de aplicaciones empresariales con conocimiento actualizable son RAG, no fine-tuning. RAG es actualizable en horas. Fine-tuning requiere días de proceso y coste computacional significativo.

Combinarlos es válido: fine-tuning para comportamiento, RAG para conocimiento. Pero empieza con RAG solo — en el 80% de los casos es suficiente.

---

### Decisión de diseño (cierre, ~1 min)

La decisión que necesitas tomar después de esta lección: para tu caso de uso específico, qué parte del pipeline RAG es la más crítica de optimizar primero.

Si la base de conocimiento es pequeña y estable: el chunking es lo más importante. Un mal chunking produce retrieval pobre independientemente de lo buena que sea la base de datos vectorial.

Si la base de conocimiento es grande y el retrieval devuelve chunks irrelevantes: añade reranking antes de invertir en mejor chunking.

Si el coste de la fase de ingestión es el problema: paraleliza el embedding. Es embarrassingly parallel — cada chunk es independiente.

Si la latencia de query es el problema: pgvector con índice HNSW bien configurado resuelve el 90% de los casos de latencia en retrieval.

Siguiente lección: chunking y reranking — el problema más subestimado del RAG y cómo resolverlo.
