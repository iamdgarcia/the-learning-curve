# Evaluación de contextos: cómo saber si tu contexto funciona

**Semestre:** 5 — Context Engineering
**Lección:** 5.7
**Duración estimada:** 9-11 min
**Formato visual:** Excalidraw (dashboard de métricas RAG + pipeline de evaluación offline/online)

---

## Objetivo de la lección

Al terminar esta lección, el alumno diseña un sistema de evaluación de contextos con métricas concretas para RAG y para agentes, y puede distinguir qué evaluar offline y qué monitorizar online.

---

## Guión

### Intro (25 seg)

Puedes implementar el mejor pipeline de chunking, el mejor modelo de embeddings, y la arquitectura de memoria más sofisticada — y aun así no saber si tu contexto funciona. Sin evaluación, estás volando a ciegas.

Esta lección cubre cómo medir la calidad del contexto con métricas concretas, cómo construir un sistema de evaluación, y cómo diferenciarlo entre offline y online.

---

### Bloque 1 — Por qué la evaluación de contextos es diferente (1.5 min)

Evaluar un sistema de IA con LLMs es distinto de evaluar software convencional. Las salidas son no deterministas. No hay una respuesta "correcta" binaria para la mayoría de preguntas. Y el comportamiento puede cambiar con el modelo, con el contexto, y con el tiempo.

Pero el que sea difícil no significa que no sea posible. Significa que necesitas métricas diseñadas específicamente para este dominio.

La evaluación de contextos tiene dos dimensiones:

**Calidad del retrieval:** ¿los documentos correctos están llegando al contexto? El LLM puede razonar perfectamente con el contexto incorrecto y producir un output incorrecto — y la culpa no es del LLM.

**Calidad de la generación dado el contexto:** dado que el contexto es correcto, ¿el LLM usa ese contexto de forma efectiva para generar una respuesta correcta?

Si el output es incorrecto, necesitas saber en cuál de las dos fases está el problema. Sin métricas separadas para cada fase, no puedes diagnosticar.

---

### Bloque 2 — Métricas para RAG: el framework RAGAS (3 min)

RAGAS (Retrieval Augmented Generation Assessment) es el framework más usado para evaluar sistemas RAG. Define cuatro métricas fundamentales:

**1. Faithfulness (fidelidad):** ¿la respuesta generada está soportada por los documentos recuperados? Mide si el LLM está alucinando o usando el contexto para fundamentar su respuesta.

Implementación: dado el contexto y la respuesta, ¿cada claim de la respuesta puede trazarse a un fragmento del contexto? Se evalúa con un LLM juez (LLM-as-a-judge) que extrae los claims de la respuesta y verifica si están en los documentos.

Rango: 0 a 1. Un sistema bien calibrado debería estar por encima de 0.85 para la mayoría de dominios.

**2. Answer Relevance:** ¿la respuesta generada es relevante para la pregunta del usuario? Mide si el LLM se fue por las ramas o respondió exactamente lo que se preguntó.

Implementación: dado la pregunta y la respuesta, el LLM juez genera preguntas hipotéticas que el usuario podría haber hecho dado la respuesta, y calcula la similitud semántica entre esas preguntas hipotéticas y la pregunta original. Alta similitud = alta relevancia.

**3. Context Recall:** ¿el retrieval trajo toda la información necesaria para responder la pregunta? Mide si los documentos recuperados cubren la respuesta esperada.

Implementación: comparas la respuesta de referencia (ground truth) con los documentos recuperados. ¿Cuántos fragmentos de la respuesta de referencia están soportados por los documentos?

Requiere un ground truth: necesitas saber cuál debería ser la respuesta correcta.

**4. Context Precision:** de los documentos recuperados, ¿qué proporción era realmente relevante? Mide el ruido en el retrieval.

Si recuperas 10 chunks y solo 3 eran relevantes para la respuesta, tu context precision es 0.3. Un retrieval ruidoso obliga al LLM a filtrar activamente qué ignorar — y a veces no lo hace correctamente.

---

### Bloque 3 — Métricas para agentes (2 min)

Los sistemas agénticos necesitan métricas adicionales porque el contexto no solo incluye documentos — incluye resultados de herramientas, historial de razonamiento, y estado de la tarea.

**Goal completion rate:** ¿el agente completa la tarea que se le asignó? La métrica más directa y la más importante. Requiere definir qué significa "completar" para cada tipo de tarea — que puede no ser trivial.

**Context utilization:** de todo el contexto disponible, ¿qué proporción usa el agente activamente para razonar? Un agente que tiene 5000 tokens de contexto pero solo usa 200 tokens relevantes para razonar tiene baja utilización — señal de que hay ruido en el contexto o de que el razonamiento es superficial.

Se mide con LLM-as-a-judge: dado el contexto y el output de razonamiento del agente, ¿qué partes del contexto fueron invocadas explícitamente?

**Irrelevant context ratio:** qué proporción del contexto inyectado es irrelevante para la tarea. Complementario a context utilization. Alta irrelevancia = retrieval pobre o acumulación de historial innecesario.

**Tool call accuracy:** para agentes con herramientas, ¿las herramientas fueron llamadas con los parámetros correctos y en el orden correcto? Mide si el agente está usando sus herramientas efectivamente.

---

### Bloque 4 — El golden dataset: el activo más valioso (1.5 min)

Todas las métricas anteriores requieren datos de referencia: preguntas con respuestas esperadas conocidas. Ese conjunto de datos es el golden dataset, y es el activo más valioso de tu sistema de evaluación.

Cómo construirlo:
- Toma un sample representativo de las consultas reales que tu sistema recibe.
- Para cada consulta, define la respuesta ideal: qué debería decir, qué documentos debería usar, qué herramientas debería llamar.
- Revisa manualmente y valida la calidad de esas respuestas de referencia.

Tamaño mínimo: 50-100 ejemplos para empezar. Suficiente para detectar regresiones claras. 200-500 para análisis estadísticamente significativo.

El golden dataset necesita mantenimiento: cuando el dominio o los documentos cambian, algunas respuestas de referencia se vuelven obsoletas. Trátalo como código — versionado, revisado, actualizado.

La buena noticia: puedes usar el LLM para generar el dataset inicial. Dado un documento, el LLM genera preguntas que podría responder con ese documento y sus respuestas esperadas. Luego revisas manualmente las más críticas. Ahorra el 80% del trabajo de construcción.

---

### Bloque 5 — Evaluación offline vs online (1.5 min)

**Evaluación offline:** ejecutas las métricas sobre el golden dataset antes de un deploy. Es el gate de calidad. Si faithfulness cae por debajo de 0.80 o goal completion rate cae más del 5% respecto al baseline, el deploy no pasa.

La evaluación offline responde: "¿este cambio mejora o empeora el sistema?"

**Monitorización online:** en producción, monitorizar continuamente métricas derivables sin ground truth. No tienes la respuesta correcta para cada consulta real, pero puedes medir:
- Distribución de longitud de respuestas (anomalías pueden señalar drift o poisoning)
- Tokens de contexto por llamada (detección de crecimiento anómalo)
- Tasa de respuestas con score bajo de faithfulness (LLM-as-a-judge en muestra aleatoria)
- Latencia por percentil
- Tasa de errores de herramientas en agentes

La monitorización online responde: "¿el sistema en producción se está comportando como esperamos?"

El circuito completo: golden dataset → evaluación offline (gate de CI/CD) → deploy → monitorización online → incidentes detectados → ampliar golden dataset → volver a evaluar.

---

### Decisión de diseño (cierre, ~1 min)

La decisión que necesitas tomar después de esta lección: por dónde empiezas cuando no tienes aún un sistema de evaluación.

**Primer paso, esta semana:** construye un golden dataset de 50 preguntas para el caso de uso principal de tu sistema. No hace falta que sea perfecto. Que sea representativo.

**Segundo paso:** implementa faithfulness y context precision con RAGAS sobre ese golden dataset. Establece tu baseline actual. Ahora cada cambio tiene referencia.

**Tercer paso:** añade la evaluación al pipeline de CI. Que cualquier cambio en el chunking, el retrieval, o el system prompt dispare la evaluación automáticamente.

Lo que no debes hacer: esperar a tener el sistema de evaluación perfecto antes de evaluar. El golden dataset imperfecto de hoy te dice más que el sistema de evaluación perfecto de dentro de tres meses.

Sin evaluación, todas las decisiones de context engineering son intuición. Con evaluación, son ingeniería.

- Anotación lateral: `"todas calculadas por LLM-as-a-judge sobre golden dataset"`

*Zona derecha — "Métricas de agentes":*
- Lista vertical:
  - `Goal completion rate` — `"¿tarea completada? métrica más importante"`
  - `Context utilization` — `"¿qué % del contexto usó para razonar?"`
  - `Irrelevant context ratio` — `"ruido en el contexto"`
  - `Tool call accuracy` — `"parámetros y orden correctos"`

*Zona inferior — "Ciclo evaluación":*
- Ciclo circular con flechas: `[Golden dataset]` → `[Evaluación offline]` → `[CI gate]` → `[Deploy]` → `[Monitorización online]` → `[Incidentes]` → `[Ampliar dataset]` → vuelve al inicio

**Flujo visual:** Los dos bloques de métricas aparecen simultáneamente (RAG a la izquierda, agentes a la derecha). El ciclo de evaluación se construye como animación circular, mostrando cómo cada etapa conecta con la siguiente. El golden dataset aparece al inicio y al final — enfatizando que es el activo central.
