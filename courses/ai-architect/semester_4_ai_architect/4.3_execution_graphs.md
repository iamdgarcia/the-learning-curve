# Execution Graphs

**Semestre:** 4 — AI Architect
**Lección:** 4.3
**Duración estimada:** 10-12 min
**Formato visual:** Excalidraw en pantalla, grafo con tres características marcadas

## Objetivo de la lección

Entender la diferencia entre el grafo de dependencias (estático) y el grafo de ejecución (dinámico), y diseñar nodos condicionales y de recuperación.

---

## Guión

### Intro (25 seg)

En la lección anterior aprendiste a construir un dependency graph. Ese grafo define la estructura del sistema: qué nodos existen, qué depende de qué, qué puede ejecutarse en paralelo.

Pero el dependency graph es estático. Describe lo que puede pasar. Lo que realmente pasa en una ejecución concreta es más complicado: hay condiciones que se cumplen o no, nodos que fallan y se reintentan, situaciones donde el sistema tiene que parar antes de llegar al final.

El execution graph captura todo eso. Es el dependency graph con comportamiento dinámico añadido.

---

### Bloque 1: Estático vs dinámico (2 min)

La distinción es importante, así que la voy a hacer precisa.

El dependency graph es tu diseño. Es el plano del sistema. Define qué nodos existen y cuáles son sus dependencias. No cambia de una ejecución a otra. Si el sistema de informe de mercado de la lección anterior tiene seis nodos, tiene seis nodos independientemente de si la búsqueda interna devuelve resultados o no.

El execution graph es lo que ocurre en una ejecución concreta. Qué rama se tomó en un nodo condicional. Cuántas veces se reintentó un nodo que falló. Si el sistema terminó antes de llegar al nodo final porque encontró una condición de error no recuperable.

Puedes pensar en ello así: el dependency graph describe el espacio de posibles ejecuciones. El execution graph describe una ejecución específica dentro de ese espacio.

Esta distinción importa para la depuración y la auditoría. Cuando algo falla, lo que inspeccionas es el execution graph de esa ejecución concreta: qué nodos se ejecutaron, en qué orden, qué outputs produjeron, dónde y por qué falló. Sin tener el execution graph, diagnosticar un fallo en un sistema multi-agente es prácticamente imposible.

---

### Bloque 2: Nodos condicionales (2.5 min)

El primer elemento dinámico del execution graph es el nodo condicional.

Un nodo condicional evalúa el output del nodo anterior y decide qué rama del grafo ejecutar a continuación. En el diagrama, se representa como un rombo, igual que en un diagrama de flujo clásico.

Un ejemplo: el sistema de informe tiene un nodo de revisión. La revisión puede producir dos resultados posibles. Primero: el borrador es aceptable y el sistema puede pasar al nodo de formato final. Segundo: el borrador tiene problemas significativos y el sistema tiene que volver al nodo de redacción con las observaciones de la revisión.

Ese nodo condicional tiene dos ramas. Y cuál de las dos se ejecuta depende del output del nodo de revisión en esa ejecución concreta.

Ahora la pregunta de diseño importante: quién evalúa la condición. Hay dos opciones.

Primera opción: código. Si la condición puede expresarse como una comparación booleana o numérica, el código es la herramienta correcta. El score de confianza del nodo de revisión es mayor que 0.8, entonces pasa. Menor que 0.8, entonces vuelve a redactar. Eso es código. Determinista, rápido, auditable.

Segunda opción: LLM. Si la condición requiere interpretar lenguaje natural o hacer un juicio semántico, el LLM es la herramienta adecuada. "El borrador cumple con los requisitos de tono y estructura del cliente" no es una comparación numérica. Es un juicio. Un LLM evaluador puede leer el borrador y el criterio, y emitir ese juicio.

Esta decisión, cuándo usar código y cuándo usar LLM para evaluar condiciones, la vamos a trabajar en la sección de cierre. Es una de las decisiones de diseño más importantes en execution graphs.

---

### Bloque 3: Nodos de retry (2 min)

El segundo elemento dinámico es el nodo de retry.

Los nodos fallan. La API externa no responde. El LLM produce un output que no pasa la validación de schema. El servicio externo devuelve un error temporal. En un sistema de producción, los fallos no son excepciones, son parte normal del comportamiento del sistema. El diseño tiene que manejarlos explícitamente.

El retry es la respuesta al fallo transitorio. Si el nodo falla, intenta de nuevo. Pero hay matices importantes en cómo diseñas el retry.

El retry simple es: si falla, intenta exactamente lo mismo de nuevo hasta N veces. Funciona para fallos de red o errores temporales de servicios externos, donde el problema no está en el input sino en la disponibilidad del servicio.

El retry con contexto es diferente: si el nodo falla, el siguiente intento incluye información sobre el fallo. Por qué falló, qué salió mal, qué debería hacerse diferente. Para nodos donde el LLM produce el output, el retry con contexto es mucho más efectivo. Si el LLM generó un JSON malformado, el siguiente intento con el mensaje de error de validación incluido en el prompt tiene mucha más probabilidad de producir el output correcto.

Lo que hay que definir en el diseño: cuántos reintentos son aceptables antes de escalar, si el retry incluye o no el contexto del error, y qué pasa cuando se agotan los reintentos. Esa última pregunta es crítica y lleva al tercer elemento.

---

### Bloque 4: Terminación anticipada (2 min)

El tercer elemento dinámico del execution graph es la terminación anticipada, o early exit.

Un sistema sin condición de terminación explícita es un sistema que puede quedarse ejecutando indefinidamente cuando algo sale mal. Eso no es aceptable en producción.

La terminación anticipada dice: si el sistema detecta que no puede completar la tarea, para. No ejecutes más nodos. No consumas más recursos. Devuelve un error informativo.

El caso más obvio es cuando se agotan los reintentos en un nodo crítico. Si el nodo de búsqueda externa falla cinco veces consecutivas, el sistema de informe de mercado no puede completar su tarea: le falta información esencial. La terminación anticipada en ese punto evita que el sistema siga ejecutando nodos de análisis, redacción y revisión sobre información incompleta, produciendo un informe de calidad inacceptable que llega al usuario como si fuera válido.

Hay otro tipo de terminación anticipada menos obvio pero igualmente importante: la detección de inutilidad. Si el nodo de análisis detecta que la empresa sobre la que se pide el informe no tiene datos suficientes en ninguna fuente disponible, puede ser más honesto parar el sistema y comunicar eso que producir un informe con datos inventados o insuficientes.

El diseño de la terminación anticipada requiere identificar, para cada sistema, cuáles son las condiciones que hacen imposible o inútil completar la tarea. Esas condiciones tienen que estar explícitamente codificadas en el execution graph.

El error más común que veo en sistemas multi-agente en producción: execution graphs sin condición de terminación explícita. El sistema puede quedar ejecutando nodos en bucle hasta que el timeout del sistema completo lo detiene, o peor, hasta que el usuario cancela manualmente después de varios minutos de espera.

---

### Bloque 5: LLM vs código en el runtime (1.5 min)

En sistemas de producción, el execution graph raramente es completamente determinista o completamente dinámico. La mayoría mezcla los dos.

En sistemas deterministas, todas las condiciones del execution graph están en código. El LLM ejecuta nodos pero no decide las ramas. Eso hace el sistema predecible y auditable, pero rígido: si aparece un caso que el diseñador no anticipó, el sistema no sabe cómo manejarlo.

En sistemas dinámicos, el LLM puede decidir qué rama tomar, si reintentar o escalar, si continuar o terminar anticipadamente. Eso da flexibilidad para casos no anticipados, pero hace el sistema mucho más difícil de predecir y depurar. Un error en el razonamiento del LLM puede hacer que el sistema tome una rama completamente incorrecta sin ninguna señal de alarma visible.

La regla de diseño es la misma que en los nodos condicionales: si la condición puede expresarse como lógica booleana o comparación numérica, código. Si requiere un juicio semántico o interpretar lenguaje natural, LLM. Y cuando uses LLM para decisiones de control del grafo, añade siempre un mecanismo de logging explícito del razonamiento que llevó a esa decisión, porque lo vas a necesitar cuando algo salga mal.

---

### Decisión de diseño (cierre, ~1.5 min)

La decisión de diseño central de esta lección: qué condiciones se evalúan con LLM y qué con código.

La regla que yo aplico es esta. Código si la condición puede expresarse como lógica booleana o comparación numérica. El score supera un umbral, el conteo está dentro de un rango, el campo obligatorio está presente, la respuesta es un JSON válido. Eso es código.

LLM si la condición requiere interpretar lenguaje natural o emitir un juicio semántico. El tono es apropiado para el cliente, el contenido es factualmente coherente, la respuesta aborda la pregunta del usuario. Eso requiere comprensión de lenguaje, y el LLM es la herramienta adecuada.

El motivo de esta regla no es filosófico. Es práctico. Las condiciones de código son deterministas y auditables. Puedes testearlas, puedes escribir casos de prueba que las cubran. Las condiciones de LLM no son deterministas, tienen un costo por llamada, y depurarlas cuando producen el resultado incorrecto es más difícil. Úsalas donde son necesarias, no donde son convenientes.

En la siguiente lección, el paso final de este bloque: cómo eliges el nivel correcto de dinamismo para un sistema completo, y por qué esa elección tiene consecuencias que van mucho más allá del diseño técnico.

## Spec del diagrama

**Tipo:** Excalidraw
**Elementos:**
- Grafo completo integrado de 6-7 nodos de ejemplo (sistema de informe u otro sistema similar)
- **Característica 1 — Nodo condicional:**
  - Un nodo en forma de rombo con etiqueta "Condicion: score >= 0.8?"
  - Dos aristas salientes: una etiquetada "Si — continúa al siguiente nodo" y otra etiquetada "No — vuelve a redactar con feedback"
  - Nota lateral: "Condición numérica → código / Juicio semántico → LLM"
- **Característica 2 — Nodo de retry:**
  - Un nodo con una flecha curva que vuelve sobre sí mismo (auto-loop)
  - Etiqueta en el loop: "hasta 3 intentos"
  - Etiqueta en la flecha de entrada al loop: "+ contexto del error"
  - Arista saliente al nodo siguiente: "éxito"
  - Arista saliente a un punto de terminación: "3 fallos → escala"
- **Característica 3 — Early exit:**
  - Un nodo con dos aristas salientes: una hacia el siguiente nodo en el flujo normal, y una directa hacia un nodo de "FIN — error" que bypasea el resto del grafo
  - La arista de early exit etiquetada: "datos insuficientes — terminar"
  - El nodo de FIN diferenciado visualmente (color diferente o borde grueso)
- Los tres elementos integrados en un único grafo coherente con flujo visible de arriba hacia abajo
**Flujo visual:** El grafo se presenta completo. Cada una de las tres características se destaca por turnos con un recuadro o anotación cuando se explica. Los tres elementos son visualmente distinguibles entre sí: el rombo para condición, el loop para retry, la flecha directa a FIN para early exit.
