# Diseñar para el fallo

**Semestre:** 4 — AI Architect
**Lección:** 4.8
**Duración estimada:** 10-12 min
**Formato visual:** Excalidraw, diagrama de flujo con mecanismos de resiliencia

## Objetivo de la lección

Asumir que los agentes van a fallar y diseñar el sistema para tolerarlo, no para evitarlo.

---

## Guión

### Intro (30 seg)

En ingeniería de sistemas distribuidos hay un principio que todos conocen pero que en sistemas de agentes se olvida constantemente: los componentes van a fallar. No es una posibilidad. Es una certeza.

En un sistema de microservicios, diseñas para la resiliencia desde el primer día porque sabes que los servicios se caen, que la red es poco fiable, que los recursos se agotan. En un sistema de agentes, exactamente lo mismo es cierto, más los problemas específicos de los LLMs: alucinaciones, timeouts, outputs que no cumplen el esquema esperado, respuestas vacías.

Si tu sistema no está diseñado para tolerar esos fallos, no es un sistema de producción. Es un prototipo.

---

### Bloque 1: El cambio de mentalidad (2 min)

El primer paso no es técnico. Es un cambio de perspectiva sobre qué significa un fallo en un sistema LLM.

En sistemas deterministas, el fallo suele ser binario y reproducible. El servicio falla o no falla. Si falla, el error es reproducible porque las mismas entradas producen el mismo fallo. Puedes depurar, corregir y verificar que el fallo desapareció.

En sistemas LLM, el fallo es estocástico. El mismo input puede producir un output válido nueve veces y un output inválido la décima. La alucinación ocurre en condiciones que no puedes siempre predecir. El timeout ocurre cuando el proveedor de API está bajo carga. El output no cumple el esquema esperado porque el modelo generó un formato ligeramente diferente al que le pediste.

Esos fallos no se pueden eliminar por diseño. No hay ninguna cantidad de instrucciones en el prompt que garantice que un LLM no va a alucinar nunca. No hay ningún nivel de especificidad en el esquema de output que garantice que el modelo siempre lo va a respetar.

Lo que sí puedes hacer es diseñar el sistema para que esos fallos sean contenibles: locales a un agente, recuperables sin reiniciar el proceso completo, observables para que puedas detectarlos y rastrearlos.

La mentalidad que necesitas es la del ingeniero de sistemas distribuidos, no la del desarrollador de aplicaciones. En sistemas distribuidos, la pregunta no es cómo evitar el fallo. La pregunta es cuánto fallo puede tolerar el sistema antes de que el servicio se degrade por debajo del nivel aceptable.

---

### Bloque 2: Los tres niveles de resiliencia (3.5 min)

El diagrama muestra un agente con tres mecanismos de resiliencia integrados. Los vemos de más local a más sistémico.

El primer nivel es el retry con backoff. El agente falla. En lugar de propagar el error inmediatamente hacia arriba, el sistema espera un tiempo y lo intenta de nuevo. El tiempo de espera crece con cada reintento para no saturar el sistema: si el proveedor de API está bajo carga, reintentar inmediatamente va a fallar por la misma razón. Esperar reduce la carga y da margen al sistema para recuperarse.

Dos detalles que marcan la diferencia entre un retry bien implementado y uno mal implementado. El primero: el retry debe incluir el contexto del error. Si el agente recibió un output que no cumple el esquema esperado, el segundo intento debe saber qué falló y por qué. No basta con enviar el mismo prompt. El prompt del reintento debe incluir: "el intento anterior falló porque el output no tenía el campo X. Por favor incluye ese campo." Eso convierte el reintento en un proceso de corrección, no en una repetición ciega.

El segundo detalle: el retry tiene un máximo de intentos. Tres o cuatro es lo habitual. Si después de cuatro intentos el agente sigue fallando, el retry no es la solución. El problema es más profundo: el task no es ejecutable con el contexto que tiene el agente, o el modelo no tiene la capacidad para ese tipo de tarea en esas condiciones.

El segundo nivel de resiliencia es el fallback. Si el agente principal falla después de agotar sus reintentos, hay un path alternativo. Ese path alternativo puede ser un agente más simple con un modelo de menor capacidad que tiene menos riesgo de timeout. Puede ser un path determinista que produce una respuesta degradada pero útil. Puede ser una respuesta enlatada que informa al usuario que esa parte del sistema no pudo completar la tarea.

El fallback no tiene que producir el mismo output de alta calidad que el agente principal. Tiene que producir algo. Un resultado degradado que el sistema puede usar para continuar es infinitamente mejor que un error que detiene el pipeline completo.

El tercer nivel es el circuit breaker. Si un agente falla más de un umbral de veces en un periodo de tiempo definido, se activa el circuit breaker: el agente se desactiva temporalmente y el sistema redirige todo el trabajo de ese agente al fallback o al path alternativo.

El circuit breaker previene que un agente que está fallando de forma sistemática consuma tokens en reintentos fallidos. Si el agente ha fallado diez veces en los últimos cinco minutos, el undécimo intento también va a fallar. No tiene sentido intentarlo. La lógica del circuit breaker dice: deja de intentarlo durante un tiempo, usa el path alternativo, y después de un periodo de recuperación prueba si el agente vuelve a funcionar.

---

### Bloque 3: Checkpointing (1.5 min)

Los tres niveles de resiliencia anteriores gestionan el fallo de un agente individual. El checkpointing gestiona el fallo del sistema completo.

Un checkpoint es un punto de guardado del estado del sistema. Después de cada etapa completada con éxito, el sistema persiste el estado actual. Si el sistema falla a mitad del proceso, puede reanudarse desde el último checkpoint en lugar de empezar desde cero.

El impacto en coste y latencia de un buen sistema de checkpointing es enorme para tareas largas. Un pipeline de análisis que tarda veinte minutos y cuesta doce dólares en tokens no debería perder todo ese trabajo si falla en el último paso. Con checkpointing, el sistema reanuda desde el paso anterior y completa el trabajo con el coste marginal del último paso.

La granularidad del checkpointing tiene un trade-off. Checkpoints después de cada paso significa overhead de escritura constante pero máxima granularidad de recuperación. Checkpoints solo en las etapas más costosas reduce el overhead pero acepta que algunos pasos intermedios puedan tener que repetirse.

La regla práctica: pon un checkpoint después de cada etapa cuyo coste de re-ejecución sea mayor que el coste de guardarlo. Para etapas baratas y rápidas, no merece la pena. Para etapas que implican análisis extenso o llamadas costosas, el checkpoint es obligatorio.

---

### Bloque 4: Fallo de agente vs fallo de sistema (1 min)

Hay una distinción que el AI Architect necesita tener clara: la diferencia entre el fallo de un agente y el fallo del sistema.

Un agente puede fallar sin que el sistema falle. Si hay un mecanismo de fallback, el sistema continúa por un path alternativo. El output puede ser de menor calidad, pero el sistema no se detiene.

El sistema solo falla cuando no hay ningún path alternativo disponible. Cuando el agente principal falla, el circuit breaker está activo, y el fallback también falla. En ese momento, el sistema no tiene ninguna opción para continuar esa tarea. Eso es el fallo del sistema.

El diseño del AI Architect consiste en definir cuántos fallos simultáneos puede tolerar el sistema antes de que el sistema mismo falle. Esa es una pregunta de requisitos tanto como de diseño. Cuánta degradación es aceptable. Cuántas tareas pueden fallar en paralelo antes de que el resultado general sea inutilizable.

Para tareas críticas, el sistema necesita redundancia en todos los niveles. Para tareas secundarias, puede ser aceptable que fallen con un mensaje de error informativo. El diseñador define esas fronteras.

---

### Bloque 5: Observabilidad como prerequisito (1 min)

Ninguno de los mecanismos de resiliencia descritos funciona si no puedes detectar el fallo en primer lugar.

Observabilidad no es un añadido después de que el sistema está en producción. Es una parte del diseño. Cada fallo de agente debe ser registrado con el agente que falló, el input que recibió, el output que produjo o el error que generó, y el momento en que ocurrió. Cada activación de retry, cada activación de fallback, cada activación de circuit breaker debe ser un evento observable.

Sin observabilidad, un agente puede estar fallando el veinte por ciento de las veces y el sistema puede estar usando el fallback el veinte por ciento de las veces sin que ningún operador lo sepa. El sistema da la apariencia de funcionar, pero la calidad del output ha degradado porque el fallback produce resultados de menor calidad que el agente principal.

La observabilidad es lo que convierte el fallo en información. Y la información es lo que permite al equipo de operaciones detectar, diagnosticar y corregir problemas antes de que el fallo de un agente se convierta en una degradación sistémica invisible.

---

### Decisión de diseño (1.5 min)

El ejercicio concreto es simple pero puede ser incómodo.

Para cada agente de tu sistema, hazte tres preguntas. Primera: ¿qué pasa si este agente falla? Segunda: ¿hay un mecanismo de retry? Tercera: ¿hay un fallback?

Si la respuesta a la segunda y la tercera pregunta es no, ese agente es un single point of failure. Si ese agente falla, el sistema se detiene. Completo. Eso puede ser aceptable en un prototipo. No lo es en producción.

El umbral mínimo para un sistema de producción es que cada agente tenga retry con un número máximo de intentos. El umbral recomendado es que cada agente crítico tenga retry más fallback. El umbral robusto es retry más fallback más circuit breaker para agentes que han demostrado tasas de fallo variables.

Y para cada etapa costosa del pipeline: checkpoint. No esperes al fallo para implementarlo. El fallo va a llegar en el momento más inoportuno, sobre la tarea más costosa, cuando el usuario más lo necesita.

El diseño para el fallo no es pesimismo. Es profesionalismo. Es lo que separa un sistema que puede operar indefinidamente en producción de uno que funciona en demos y falla bajo carga real.

## Spec del diagrama

**Tipo:** Excalidraw, diagrama de flujo vertical

**Elementos:**
- Flecha de entrada al diagrama con etiqueta "Input"
- Rectángulo "Agente" (centro)
- Rombo de decisión "¿Éxito?" a la derecha del agente
- Path de éxito (sí): flecha a "Output" → rectángulo "Checkpoint" marcado en verde después del output exitoso
- Path de fallo (no): flecha a contador "Reintentos: N/max"
  - Subrombo: "¿Reintentos agotados?"
  - No: flecha de vuelta al agente con etiqueta "Retry + contexto del error" (flecha curva)
  - Sí: flecha a subrombo "¿Circuit breaker activo?"
    - Sí: flecha a rectángulo "Fallback / Path alternativo" (marcado en amarillo)
    - No: flecha a rectángulo "Escalación / Error sistémico" (marcado en rojo)
- Etiquetas de observabilidad: pequeños iconos de registro en cada transición de fallo con etiqueta "log"
- Leyenda: "Verde = operación normal | Amarillo = degradado pero funcional | Rojo = fallo de sistema"

**Flujo visual:** Flujo vertical de arriba a abajo para el path feliz. Los paths de fallo se ramifican hacia la derecha y regresan hacia arriba (retry) o continúan hacia abajo (fallback, escalación). El checkpoint aparece como un símbolo de disco justo después del output exitoso, antes de continuar al siguiente nodo del grafo.
