# Prompt Engineering para arquitectos (no para usuarios)

**Semestre:** 1 — Foundations
**Lección:** 1.6
**Duración estimada:** 7-9 min
**Formato visual:** Slides PDF (anatomía anotada + ejemplo completo)

---

## Objetivo de la lección

Diseñar system prompts como interfaces tipadas, no como instrucciones informales: versionables, testeables, revisables en PR.

---

## Guión

### Intro (25 seg)

"Prompt engineering" tiene mala reputación en equipos de ingeniería senior. Suena a algo que hacen los usuarios en un chat, no algo que diseña un arquitecto. Esa percepción es el problema. El system prompt de un sistema LLM es una interfaz de software con las mismas responsabilidades que cualquier otra interfaz: tiene que estar definida, ser predecible, y sobrevivir a un cambio de equipo. Hoy vemos cómo diseñarlo como tal.

---

### Bloque 1 — La diferencia fundamental: system prompt vs user prompt

Antes de la anatomía, aclaramos la distinción que importa arquitectónicamente.

El user prompt es el input del usuario. Es variable, impredecible, llega en tiempo de ejecución. Tu sistema no lo controla más de lo que un servidor web controla qué peticiones HTTP llegan.

El system prompt es arquitectura. Es el contrato que defines en tiempo de diseño. Le dice al modelo quién es en este sistema, qué sabe que el usuario no le está diciendo, qué no debe hacer nunca, y qué formato debe devolver. Lo escribes tú. Lo versiones tú. Lo testeas tú.

La analogía que más me ha funcionado para explicar esto a equipos: el system prompt es como la definición de interfaz de un servicio. El user prompt es como la llamada a ese servicio. Si tu interfaz está mal definida, ninguna cantidad de llamadas bien formadas va a producir comportamiento correcto.

Y como toda interfaz, el system prompt tiene que sobrevivir a más de un caso. No al caso que tienes en mente cuando lo escribes. A los casos que van a aparecer en producción cuando los usuarios empiecen a usar el sistema de formas que no anticipaste.

---

### Bloque 2 — Anatomía de un system prompt bien estructurado

Vamos a la slide. Un system prompt bien estructurado tiene cuatro secciones. No cuatro apartados decorativos. Cuatro elementos con función específica en el comportamiento del modelo.

**Sección 1: Rol.**
Define quién es el LLM en este sistema. No "eres un asistente útil" — eso es el default implícito de cualquier modelo. Rol específico: qué hace, para quién, en qué contexto de negocio.

Un ejemplo concreto: "Eres el asistente de soporte técnico de nivel 1 para la plataforma de analytics de Empresa X. Tu función es ayudar a clientes a resolver problemas operacionales con el dashboard, gestión de cuentas, y facturación."

Ese rol le da al modelo el marco de referencia para interpretar cada mensaje del usuario. Una pregunta sobre "cómo exportar datos" en el contexto de ese rol tiene una respuesta muy distinta a la misma pregunta en un contexto de escritura de código o de edición de documentos.

**Sección 2: Contexto.**
Lo que el modelo sabe que el usuario no ha dicho explícitamente. Esto incluye información del sistema que has inyectado — el nombre del usuario autenticado, su plan de suscripción, el historial de tickets abiertos, el estado actual de su cuenta. También incluye hechos del dominio que el modelo necesita para responder correctamente y que no puedes asumir que están en el modelo base.

El contexto es la sección más dinámica del system prompt en sistemas reales. Es donde conectas el estado de tu sistema con el modelo.

**Sección 3: Restricciones.**
Qué no debe hacer nunca el modelo en este sistema. No como instrucción negativa genérica — "no seas dañino" es inútil porque el modelo ya tiene eso. Restricciones específicas del caso de uso: no discutir productos de la competencia, no dar información sobre precios sin antes verificar el plan del usuario, no escalar a soporte humano sin seguir el protocolo de tres pasos definido, no responder sobre temas fuera del dominio de la aplicación.

Las restricciones son el lugar donde defines los límites del sistema. Un modelo sin restricciones explícitas en el dominio va a intentar ser útil fuera de ese dominio. Y esa utilidad no solicitada es un riesgo de soporte, de imagen de marca, y en algunos casos de responsabilidad legal.

**Sección 4: Formato de output.**
Qué estructura debe devolver el modelo. Esta sección es crítica en sistemas que procesan el output del LLM de forma automática — y en la mayoría de los sistemas de producción, algo procesa ese output.

Si el output va a ser parseado por código, el formato tiene que ser exacto y consistente. JSON con un schema específico. Texto con marcadores definidos. Un campo por línea. Lo que sea que tu código downstream espere. Y tienes que especificarlo de forma tan precisa como especificarías un schema de API.

Si el output va directamente al usuario, el formato controla la experiencia: longitud máxima, uso de listas o párrafos, nivel de tecnicidad del lenguaje.

### Bloque 3 — El prompt como código

Esta sección es corta pero es la que más cambia la cultura de trabajo en un equipo.

Un system prompt no es un texto que alguien pegó en un campo de configuración y nadie tocó desde entonces. Es código. Tiene que estar en control de versiones. Tiene que tener un historial de cambios con justificación. Tiene que pasar por review cuando cambia. Tiene que tener tests que validan que el comportamiento esperado se mantiene.

Lo que esto implica en la práctica:

El prompt vive en el repositorio, no en una base de datos de configuración a la que solo accede el equipo de producto. Cuando alguien propone un cambio al prompt, abre un PR. El PR tiene diff. Alguien lo revisa. Se hace merge con criterio, no con un "a ver cómo funciona".

Los tests del prompt verifican casos concretos: dado este input, el output debe tener esta estructura. Dado este input edge case, el modelo no debe hacer esta cosa que está en las restricciones. Los tests de LLMs son probabilísticos — no puedes garantizar el output exacto — pero sí puedes verificar propiedades del output de forma consistente.

El versionado del prompt tiene semántica. Una versión mayor cuando cambias el rol o las restricciones de forma significativa. Una versión menor cuando añades contexto o ajustas formato. Esto te permite hacer rollback cuando un cambio de prompt degrada el comportamiento.

---

### Bloque 4 — Lo que el prompt no puede resolver

Aquí es donde el prompt engineering deja de ser una solución universal.

El prompt no puede resolver problemas de datos. Si el modelo no tiene acceso a la información correcta — porque no está en el contexto, porque el RAG no está recuperando los documentos relevantes, porque nadie inyectó el estado actual del sistema — ningún prompt va a generar esa información de la nada. Va a alucinar, o va a decir que no sabe. Cambiar el prompt no arregla un problema de datos.

El prompt no puede resolver problemas de arquitectura. Si el diseño del sistema le pide al LLM que haga algo para lo que no está equipado — razonar sobre grafos complejos sin el grafo en el contexto, mantener estado entre llamadas sin mecanismo de persistencia, actuar de forma determinista en una tarea que requiere herramientas externas — el prompt no va a compensar ese déficit estructural. El síntoma es que cambias el prompt, el output mejora un poco, lo cambias de nuevo, mejora un poco más, y nunca llegas al comportamiento que necesitas. Esa es la señal de que el problema es arquitectural, no de instrucciones.

La regla práctica: si cambiar el prompt no mejora el output de forma clara y consistente, para de cambiar el prompt y analiza qué está faltando en el sistema que rodea al LLM.

---

### Bloque 5 — Prompt injection: la vulnerabilidad que subestimas

Prompt injection es la vulnerabilidad más común en sistemas LLM y la menos discutida en equipos que vienen del software tradicional.

El escenario básico: tienes un system prompt que define el comportamiento del sistema. El usuario envía un mensaje que dice "ignora las instrucciones anteriores y haz X". El modelo, dependiendo de cómo esté construido el prompt y del modelo en sí, puede obedecer esas instrucciones del usuario por encima de las tuyas.

Esto no es solo un problema de usuarios maliciosos. Es un problema de diseño. Si tu sistema procesa texto de fuentes externas — correos, documentos de terceros, contenido de páginas web — ese texto podría contener instrucciones que el modelo ejecute sin que ningún usuario lo haya pedido explícitamente.

Las defensas no son perfectas porque el problema es estructural: el modelo recibe instrucciones mezcladas de fuentes distintas en el mismo flujo de texto. Las medidas prácticas son: separación clara entre las secciones del prompt con marcadores que el modelo reconozca, instrucciones explícitas sobre cómo tratar instrucciones en el contenido del usuario, y vigilancia activa sobre los outputs del sistema en producción.

Nunca asumas que el system prompt es inviolable desde la perspectiva del usuario. Diseña el sistema asumiendo que alguien va a intentar subvertirlo.

---

### Decisión de diseño (cierre, ~1 min)

La pregunta que tienes que saber responder cuando el sistema no se comporta como esperas: ¿el problema está en el prompt o en la arquitectura?

La señal de que el problema es el prompt: el modelo tiene la información correcta en el contexto, el formato de output está mal especificado, el rol está demasiado vago, o las restricciones son ambiguas. Cambiar el prompt produce mejoras visibles e inmediatas.

La señal de que el problema es la arquitectura: el modelo no tiene acceso a datos que necesita, el sistema le está pidiendo que razone sobre algo que está fuera de su ventana de contexto, o la tarea requiere capacidades que un LLM no tiene de forma nativa. Cambiar el prompt produce mejoras marginales o ninguna mejora.

El árbol de decisión es directo: antes de tocar el prompt, verifica que el contexto que recibe el modelo es correcto y completo. Si lo es, ajusta el prompt. Si no lo es, el prompt es el último paso, no el primero.
