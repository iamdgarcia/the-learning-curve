# Verifiers y validación de outputs

**Semestre:** 3 — Agent Engineering
**Lección:** 3.3
**Duración estimada:** 7-9 min
**Formato visual:** Excalidraw animado en pantalla

## Objetivo de la lección

Diseñar una capa de validación que impida que los errores del agente lleguen al siguiente paso del sistema.

---

## Guión

### Intro (25 seg)

El agente razona, decide, actúa. Y a veces se equivoca.

Puede alucinar datos que no existen. Puede malinterpretar las instrucciones del sistema. Puede devolver un output que técnicamente tiene el formato correcto pero semánticamente no tiene ningún sentido.

Si ese output llega directamente al siguiente paso del sistema, el error se propaga. Y los errores que se propagan son mucho más difíciles de depurar que los errores que se detectan en origen.

El verifier es la capa que corta esa propagación.

---

### Bloque 1: El problema concreto (1.5 min)

El LLM no falla como falla el código determinista. El código determinista lanza una excepción cuando algo va mal. El LLM devuelve algo que parece razonable aunque esté equivocado.

Eso hace que los errores de un agente sean insidiosos. El sistema puede seguir funcionando durante ciclos completos antes de que alguien se dé cuenta de que el output era incorrecto desde el principio.

Un ejemplo: tienes un agente que extrae datos de facturas y los transforma en una estructura JSON para cargar en tu sistema financiero. El agente devuelve el JSON correcto. El schema se valida. Los datos se cargan. Pero el agente confundió el campo "total sin impuestos" con "total con impuestos". Ese error lleva tres semanas en producción antes de que alguien lo detecte en un informe.

El agente no generó un error. Generó datos incorrectos con el formato correcto. Y eso es exactamente el tipo de fallo que un verifier bien diseñado puede atrapar antes de que llegue al sistema.

---

### Bloque 2: Qué es un verifier (1 min)

Un verifier es código, o un LLM, que valida el output del agente antes de que el sistema lo use.

Su posición en el sistema es clara: el agente produce un output, el verifier lo evalúa, y solo si pasa la validación ese output avanza al siguiente paso. Si no pasa, el verifier toma una decisión: reintentar, escalar, o terminar con error.

El verifier no es parte del agente. Es una capa independiente entre el agente y el resto del sistema. Esa independencia es intencional: el verifier no confía en el agente por defecto. Su trabajo es validar, no asumir que el output es correcto.

Fíjate en el diagrama. El output del agente llega a un rombo de decisión: válido o inválido. Si es válido, avanza. Si no, el sistema tiene que decidir qué hacer con eso.

---

### Bloque 3: Tipos de verifiers (2 min)

Hay varios tipos de verifiers y cada uno valida algo distinto.

El primero es la validación de schema. ¿El output tiene el formato esperado? ¿Están los campos obligatorios? ¿Los tipos son correctos? Esto es código determinista, rápido, barato. Si el agente tiene que devolver un JSON con campos específicos, la validación de schema lo confirma sin ambigüedad.

El segundo son las reglas de negocio. ¿El output cumple las reglas que conoces del dominio? Si el agente devuelve una fecha de vencimiento anterior a la fecha de emisión, eso es un error aunque el schema sea válido. Las reglas de negocio son invariantes que puedes codificar como tests.

El tercero son los range checks. ¿Los valores numéricos están en rangos esperados? Un agente que extrae porcentajes no debería devolver 3700%. Eso se atrapa con una comprobación de rango.

El cuarto son los consistency checks. ¿El output es coherente con el input? Si el agente recibe un documento en español y devuelve un resumen en alemán, algo fue mal. Si el agente recibe cinco items para procesar y devuelve tres, algo falta.

El quinto es LLM-as-a-judge. Un segundo LLM que evalúa el output del primero según un criterio semántico. ¿El resumen captura la intención del documento original? ¿La respuesta generada responde realmente a la pregunta que se hizo? Este tipo de verificación no puede expresarse como regla determinista.

Cada uno de estos tiene un coste distinto y una capacidad distinta. Empieza por los más baratos.

---

### Bloque 4: Cuándo usar código y cuándo usar LLM (1.5 min)

La regla es directa: si puedes escribir el verifier como código determinista, escríbelo como código.

El código determinista es rápido, es barato, es repetible, no varía entre ejecuciones. Si puedes expresar el criterio de validación como una función que devuelve verdadero o falso, hazlo así.

El LLM-as-a-judge es para cuando el criterio es semántico o subjetivo y genuinamente no puede expresarse como regla. No como primer recurso. Como último recurso cuando los verifiers deterministas no son suficientes.

El error que veo: usar LLM-as-a-judge para todo porque parece más inteligente o más sofisticado. El resultado es validación cara, lenta, no determinista, y con sus propios puntos de fallo. Si el agente puede alucinar, el juez también puede alucinar.

Un buen sistema de validación empieza con schema, añade reglas de negocio y range checks, usa consistency checks donde aplique, y reserva el LLM-as-a-judge para los criterios semánticos que no tienen alternativa.

Piénsalo como capas. Las capas baratas primero. Si el output no pasa la más barata, no gastes en evaluar las más caras.

---

### Bloque 5: Qué pasa cuando el verifier falla (1.5 min)

Cuando el verifier detecta un output inválido, tienes tres caminos posibles. Los tres son válidos en distintos contextos. El que nunca es válido es el silencio.

El primero es el retry con contexto del error. El sistema devuelve el output al agente junto con información específica de qué falló. El agente intenta de nuevo con ese contexto adicional. Esto funciona cuando el error es recuperable y el agente tiene información suficiente para corregirlo.

El segundo es la escalación al supervisor. El sistema pasa el caso a un supervisor, humano u otro sistema, que decide qué hacer. Esto aplica cuando el error no es recuperable automáticamente o cuando el impacto potencial de un error es demasiado alto para reintentar sin revisión.

El tercero es la terminación con error explícito. El sistema falla limpiamente con un error descriptivo. El caso queda registrado para revisión posterior. Esto aplica cuando la situación no tiene solución automática y continuar no tiene sentido.

Ninguno de esos tres es el silencio. Que el verifier detecte un error y el sistema continúe como si nada es el peor escenario posible. Propagas el error y pierdes el punto donde ocurrió.

---

### Decisión de diseño (cierre, ~1 min)

La decisión de diseño de esta lección es qué validas con código determinista y qué con LLM-as-a-judge.

La respuesta casi siempre es: más de lo primero de lo que crees, y menos de lo segundo de lo que parece cómodo.

Antes de añadir un LLM-as-a-judge, hazte esta pregunta: ¿puedo escribir este criterio como un test unitario? Si la respuesta es sí, aunque sea parcialmente, escríbelo en código. El LLM-as-a-judge es el último recurso cuando el criterio es verdaderamente semántico y no tiene representación determinista posible.

Y recuerda: el verifier no es una señal de desconfianza en el agente. Es la capa de defensa que hace que el agente sea seguro de operar en un sistema real. Un agente sin verifier es un agente que no puedes llevar a producción con confianza.

## Spec del diagrama

**Tipo:** Excalidraw

**Elementos:**
- Bloque "Agente" a la izquierda (rectángulo)
- Flecha "output" desde Agente hacia el centro
- Rombo de decisión en el centro etiquetado "Verifier"
- Rama derecha del rombo etiquetada "Válido" con flecha hacia bloque "Siguiente paso del sistema"
- Rama inferior del rombo etiquetada "Inválido" con flecha hacia tres bloques en paralelo:
  - "Retry con contexto del error" (flecha de vuelta hacia Agente)
  - "Escalación a supervisor"
  - "Error explícito / terminación"
- Anotaciones dentro o junto al rombo de decisión con los tipos de verifiers listados:
  - "Schema validation"
  - "Business rules"
  - "Range checks"
  - "Consistency checks"
  - "LLM-as-a-judge"
- Los cuatro primeros en color neutro, LLM-as-a-judge en color diferenciado con anotación "último recurso"

**Flujo visual durante la explicación:**
1. Empieza mostrando solo el bloque Agente y la flecha hacia el rombo sin ramas
2. Se añade la rama "Válido" cuando se explica el flujo normal
3. Se añade la rama "Inválido" con los tres destinos cuando se explica qué pasa al fallar
4. Los tipos de verifiers se añaden progresivamente dentro del rombo mientras se explica cada tipo
5. LLM-as-a-judge se destaca visualmente al explicar cuándo usarlo
