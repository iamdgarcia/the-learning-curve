# Memoria en agentes: short vs long term

**Semestre:** 3 — Agent Engineering
**Lección:** 3.6
**Duración estimada:** 7-9 min
**Formato visual:** Cámara + diagrama Excalidraw con agente central y compartimentos de memoria

## Objetivo de la lección

Diseñar la capa de memoria de un agente individual, eligiendo el tipo correcto para cada necesidad.

---

## Guión

### Intro (20-30 seg)

Un agente sin memoria es un agente que empieza desde cero en cada interacción. Para muchos casos eso es suficiente. Para muchos otros no. El problema es que "memoria" es una palabra que se usa para cinco cosas distintas, y elegir mal el tipo de memoria tiene consecuencias en coste, coherencia y complejidad operativa. Esta lección te da el mapa.

---

### Bloque 1: La pregunta correcta

Antes de hablar de tipos de memoria, la pregunta que tienes que responder es esta: qué necesita recordar el agente, durante cuánto tiempo, y qué pasa si lo olvida?

Eso define todo lo demás. Si la respuesta a "qué pasa si lo olvida" es "nada grave", probablemente no necesitas persistencia. Si la respuesta es "el agente repite el mismo error que ya cometió", necesitas algún tipo de memoria entre sesiones. Si la respuesta es "el agente no puede completar la tarea que empezó ayer", necesitas estado persistente de la tarea.

No empieces por el tipo de memoria. Empieza por el ciclo de vida de la información.

---

### Bloque 2: In-context memory (short-term)

La memoria in-context es la más simple. Es la conversación actual. Todo lo que el agente sabe en este momento está en el context window: las instrucciones del sistema, el historial de la sesión, los resultados de las herramientas que ha llamado, el output que ha producido.

Las ventajas son evidentes: no requiere infraestructura adicional, el modelo tiene acceso directo a todo, y no hay latencia de recuperación.

Las limitaciones también son evidentes: se olvida cuando termina la sesión. No hay persistencia. Y tiene un coste que escala con el tamaño del contexto: más tokens en el contexto, más caro cada llamada.

Para agentes de sesión corta donde no se necesita continuidad entre conversaciones, in-context es suficiente y es la opción correcta. No añadas complejidad que no necesitas.

---

### Bloque 3: Working memory

Working memory es el estado de la tarea en ejecución. No es la conversación, es el progreso: qué pasos ha completado el agente, qué resultados intermedios ha obtenido, en qué punto está de un proceso largo.

En una tarea que dura cinco minutos y termina en una sesión, working memory vive in-context. Pero si la tarea dura horas o días, o si el agente puede ser interrumpido y debe retomar, necesitas externalizar ese estado.

La implementación práctica es un objeto de estado que el agente escribe explícitamente: "he completado los pasos 1, 2 y 3, el resultado del paso 2 fue X, el siguiente paso es 4". Ese objeto persiste en un almacén externo mientras dura la tarea, y se elimina cuando la tarea termina.

La clave de working memory es que su ciclo de vida está atado a la tarea, no al usuario ni al dominio. Cuando la tarea termina, ese estado puede desaparecer. No mezcles working memory con memoria de largo plazo.

---

### Bloque 4: Episodic memory

Episodic memory son recuerdos de interacciones pasadas específicas. "La última vez que este usuario preguntó sobre un tema, respondí de esta manera y el resultado fue este." "En la tarea del martes, cometí este error que no debería repetir."

Es el tipo de memoria que hace que un agente parezca que "te conoce". Es también el tipo que requiere más cuidado de diseño porque implica decidir qué episodios recordar, cómo recuperarlos, y cuándo son relevantes.

La implementación habitual es una base de datos que almacena resúmenes de interacciones pasadas. El agente, al inicio de una nueva interacción, recupera los episodios relevantes y los incluye en su contexto. No almacenas la conversación completa, almacenas una representación útil.

El riesgo aquí es la relevancia. Si recuperas episodios que no son relevantes para la tarea actual, contaminas el contexto. El mecanismo de recuperación es tan importante como el almacenamiento. Típicamente se usa búsqueda semántica para encontrar los episodios más similares a la situación actual.

---

### Bloque 5: Semantic memory

Semantic memory es conocimiento general sobre el dominio. No recuerdos de interacciones, sino conceptos, hechos, documentos de referencia, políticas, procedimientos.

La implementación habitual es RAG: retrieval-augmented generation. Tienes una base de conocimiento indexada, y el agente recupera fragmentos relevantes cuando los necesita.

La distinción con episodic es importante. Episodic memory es "recuerdo que esta persona prefiere respuestas cortas". Semantic memory es "el procedimiento para escalar un incidente es este". Una es personal y temporal, la otra es institucional y permanente.

Semantic memory raramente cambia. Se actualiza cuando cambia el conocimiento del dominio, no con cada interacción. Eso la hace más barata de mantener y más confiable como fuente de verdad.

---

### Bloque 6: Long-term memory y el problema del coste

Episodic y semantic son los dos tipos de long-term memory. Ambas requieren infraestructura externa: un almacén que persiste entre sesiones, un mecanismo de escritura y uno de recuperación.

El coste que mucha gente no anticipa es el de recuperación. No pagas solo por almacenar. Pagas por cada vez que el agente hace una búsqueda para recuperar información relevante. Si el agente hace tres búsquedas en memoria antes de responder, y responde diez veces por hora, eso es treinta búsquedas por hora. A escala, ese coste acumula.

La optimización es ser selectivo. El agente no debe buscar en memoria en cada paso. Debe buscar cuando la tarea lo requiere: al inicio de una nueva sesión para recuperar contexto del usuario, o cuando encuentra una situación que podría haberse visto antes.

---

### Decisión de diseño (cierre, ~1 min)

El mapa es este.

Si la información es relevante solo en la sesión actual: in-context.

Si es el estado de una tarea larga que puede interrumpirse: working memory externalizada.

Si son preferencias o historial del usuario que debe persistir entre sesiones: episodic memory.

Si son documentos, políticas o conocimiento del dominio que el agente debe consultar: semantic memory con RAG.

La trampa más común es mezclar tipos. El agente que guarda en episodic memory cosas que deberían ser working memory termina con un almacén que crece sin control y recuperaciones que contaminan el contexto con información irrelevante.

Define el ciclo de vida antes de elegir el almacén. La tecnología que uses para implementar cada tipo es secundaria.

## Spec del diagrama

**Tipo:** Excalidraw

**Elementos:**
- Caja central grande con etiqueta "Agente"
- Cuatro compartimentos de memoria alrededor del agente, uno en cada cuadrante:
  - Arriba izquierda: "In-context / Short-term" — Persistencia: sesión — Coste: medio — Ejemplo: historial de conversación
  - Arriba derecha: "Working Memory" — Persistencia: tarea — Coste: bajo — Ejemplo: progreso de tarea larga
  - Abajo izquierda: "Episodic Memory" — Persistencia: días / indefinido — Coste: medio-alto — Ejemplo: preferencias del usuario, historial de errores
  - Abajo derecha: "Semantic Memory (RAG)" — Persistencia: permanente — Coste: bajo por consulta — Ejemplo: documentos de referencia, políticas
- Flechas desde el agente hacia cada compartimento con etiquetas "R" (lectura) y "W" (escritura)
  - In-context: R + W (el agente lee y escribe constantemente)
  - Working: R + W (el agente actualiza su estado de tarea)
  - Episodic: R al inicio de sesión, W al final (o en momentos clave)
  - Semantic: solo R (el agente consulta, no modifica el conocimiento del dominio)
- Icono de base de datos junto a Episodic y Semantic para indicar almacén externo
- Icono de ventana junto a In-context y Working para indicar que viven en proceso

**Flujo visual:** El diagrama aparece con el agente en el centro. Los cuatro compartimentos se añaden secuencialmente mientras se explica cada tipo. Las flechas R/W se añaden al final para mostrar los patrones de acceso. Los iconos de persistencia (sesión / tarea / días / permanente) se destacan en color para facilitar la comparación.
