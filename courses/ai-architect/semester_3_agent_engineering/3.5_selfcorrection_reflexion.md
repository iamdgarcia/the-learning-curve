# Self-correction y reflexión en agentes

**Semestre:** 3 — Agent Engineering
**Lección:** 3.5
**Duración estimada:** 7-9 min
**Formato visual:** Cámara + diagrama Excalidraw animado en pantalla

## Objetivo de la lección

Diseñar agentes que detectan y corrigen sus propios errores sin intervención externa, y entender cuándo ese mecanismo vale el coste adicional.

---

## Guión

### Intro (20-30 seg)

Hasta ahora diseñamos cómo el agente valida lo que recibe del entorno y cómo un supervisor humano interviene cuando algo sale mal. Hoy atacamos el problema desde dentro: cómo el agente detecta y corrige sus propios errores antes de entregarlos al sistema. Eso se llama reflexión, y tiene un coste que hay que entender antes de usarlo.

---

### Bloque 1: Qué es la reflexión

Reflexión significa que el agente evalúa su propio output antes de entregarlo al sistema siguiente.

La implementación básica funciona así. El agente ejecuta una acción, produce un resultado, y luego hace una segunda llamada al LLM, esta vez en modo crítico, para evaluar lo que acaba de hacer. El resultado de esa crítica determina si el output avanza o vuelve a revisión.

Por qué esto funciona: el LLM en modo crítico tiende a detectar errores que no detectó en modo generativo. No porque sea un modelo diferente, sino porque el cambio de rol activa diferentes patrones de razonamiento. Le dices "eres un evaluador, aquí está este texto, encuéntrale problemas", y el modelo enfoca su atención de forma distinta a cuando le dices "escribe este texto". El mismo modelo. Distinto comportamiento.

Si llevas esto al diagrama en pantalla, tienes: el agente actúa, produce un output, ese output va a una fase de crítica, y el resultado es una decisión: el output es suficientemente bueno o no lo es.

---

### Bloque 2: La implementación del loop

El loop de reflexión tiene cuatro componentes.

Primero, la acción: el LLM en modo generativo produce algo. Una respuesta, un plan, un fragmento de razonamiento.

Segundo, la crítica: el mismo LLM, o uno diferente, recibe el output junto con un prompt que le pide que lo evalúe. El prompt del crítico debe ser diferente al prompt del generador. No es "revisa tu trabajo". Es "eres un revisor externo, aquí tienes estos criterios, evalúa si este output los cumple."

Tercero, la decisión: basada en la crítica, el sistema determina si el output es aceptable. Esto puede ser una evaluación del LLM crítico, o puede ser un threshold más mecánico.

Cuarto, el límite de iteraciones: siempre hay un contador. Si el agente no converge después de N ciclos, el loop termina. Sin este límite, el agente puede quedarse atascado indefinidamente si la tarea tiene una solución que no alcanza. El límite define qué pasa cuando se agota: escalación al supervisor, error explícito, o entrega del mejor resultado disponible con una flag que indica que no convergio.

En el diagrama ves esto: acción, output, crítica, rombo de decisión, y una rama que vuelve a acción con el contador decrementado, y otra que entrega al sistema.

---

### Bloque 3: El coste y el riesgo principal

El coste es directo. Cada ciclo de reflexión añade una llamada al LLM. Si tienes una tarea de 10 pasos y reflexionas en cada paso, el coste puede duplicarse o triplicarse dependiendo de cuántos ciclos necesita cada paso. Eso no es gratuito ni en latencia ni en dinero.

La pregunta que tienes que responder antes de añadir reflexión en un paso: si el agente comete un error aquí y no lo detecta, qué pasa? Si la respuesta es "el sistema lo detecta después" o "el coste del error es bajo", la reflexión en ese paso probablemente no vale. Si la respuesta es "ese error se propaga y contamina todo lo que viene después", ahí sí vale el coste adicional.

El riesgo principal es confirmation bias. El agente puede convencerse de que su error es correcto. Esto ocurre especialmente cuando el crítico y el generador comparten demasiado contexto: el modelo ya "sabe" por qué tomó esa decisión, y tiende a encontrar justificaciones en lugar de problemas.

La mitigación es variar el prompt del crítico. Introduce criterios específicos, perspectivas distintas, casos límite que el generador debería haber considerado. Si el generador produjo una respuesta técnica, el crítico puede evaluarla desde el punto de vista de alguien sin contexto técnico. El cambio de perspectiva reduce el riesgo de que el crítico simplemente valide lo que ya se decidió.

---

### Bloque 4: Reflexión vs verifier externo

Reflexión es interna. El agente se critica a sí mismo. Verifier es externo: otro componente del sistema valida el output del agente.

No son excluyentes, pero tampoco siempre necesitas ambos. La pregunta es qué tipo de error estás buscando detectar.

La reflexión es efectiva para errores de razonamiento o coherencia. Si el agente produjo un plan que contradice sus instrucciones, o una respuesta que no responde a la pregunta real, o un argumento con una premisa incorrecta, el LLM en modo crítico tiene posibilidades de detectarlo si cambia de perspectiva. El error requiere entendimiento para ser detectado.

El verifier externo es más efectivo para errores de formato, schema o reglas de negocio. Si el output debe ser un JSON con campos específicos y los campos están mal nombrados, no necesitas que el agente "entienda" el error para detectarlo. Un parser lo detecta en milisegundos con coste cero. Un verifier que valida contra un schema es determinista, rápido y no se equivoca. El agente reflexionando sobre si su JSON tiene los campos correctos es un desperdicio de tokens.

La división práctica: reflexión para errores de razonamiento, verifier para errores de estructura.

---

### Decisión de diseño (cierre, ~1 min)

La pregunta al final es simple: cuándo añadir reflexión.

La reflexión vale cuando el error que quieres detectar requiere comprensión para ser detectado, y cuando ese error no se corrige fácilmente en pasos posteriores del sistema.

No vale cuando el error es estructural o mecánico, o cuando el coste adicional supera el valor de detectarlo antes.

Y si decides añadirla, define siempre tres cosas: el prompt del crítico, que debe ser distinto al del generador; el límite de iteraciones, que define cuánto puede fallar el agente antes de escalar; y qué pasa cuando se agota ese límite. Sin esas tres decisiones, el loop de reflexión es un bucle de incertidumbre con coste ilimitado.

## Spec del diagrama

**Tipo:** Excalidraw animado (se construye en pantalla mientras se explica)

**Elementos:**
- Caja "LLM (modo generativo)" con etiqueta "Acción"
- Flecha hacia caja "Output"
- Flecha desde Output hacia caja "LLM (modo crítico)" con etiqueta "Crítica"
- Rombo de decisión con etiqueta "Suficientemente bueno?"
- Rama "SI" hacia caja "Entrega al sistema siguiente"
- Rama "NO" hacia caja "Revisión" con flecha de vuelta a LLM generativo
- Contador lateral con etiqueta "Iteraciones: N" decrementando en cada ciclo
- Caja de escape con etiqueta "Escalación / Error explícito" conectada al contador cuando llega a 0
- Nota flotante junto al LLM crítico: "Prompt distinto al generador"

**Flujo visual:** Se construye de izquierda a derecha. Primero el camino feliz (acción → output → crítica → entrega). Luego se añade el rombo y la rama de vuelta. Luego el contador. Luego la rama de escape. El diagrama completo revela el mecanismo de control progresivamente.
