# MCP: qué resuelve arquitectónicamente

**Semestre:** 2 — AI Engineering
**Lección:** 2.4
**Duración estimada:** 7-9 min
**Formato visual:** Excalidraw (dos paneles lado a lado)

---

## Objetivo de la lección

Al terminar esta lección, el alumno entiende MCP como estándar de integración entre modelos y herramientas, y sabe cuándo construir un servidor MCP propio frente a una integración directa.

---

## Guión

### Intro (25 seg)

Cuando añades herramientas externas a un sistema con LLM — una base de datos, una API interna, un sistema de ficheros, lo que sea — aparece un problema de integración que escala mal. No escala linealmente. Escala en producto cartesiano.

Esta lección es sobre el estándar que resuelve eso, y más importante, sobre lo que ese estándar implica para tu arquitectura.

---

### Bloque 1 — El problema: N modelos × M herramientas

Imagina que tienes tres modelos distintos en producción. Un modelo para soporte al cliente. Otro para análisis interno. Otro para generación de documentos. Tres sistemas con propósitos distintos, equipos distintos, ritmos de actualización distintos.

Ahora imagina que cada uno necesita acceso a cuatro herramientas: la base de datos de clientes, el sistema de tickets, el almacén de documentos, y el API de calendario.

Sin ningún estándar, ¿qué pasa? Cada modelo necesita su propia integración con cada herramienta. El equipo de soporte escribe un conector para su modelo que habla con la base de datos. El equipo de análisis escribe otro conector, diferente, para su modelo que habla con la misma base de datos. El equipo de documentos escribe un tercero.

Tres modelos por cuatro herramientas son doce integraciones. Cada una con su propia lógica de autenticación, su propio manejo de errores, su propio esquema de datos. Cuando la base de datos cambia su API, los tres equipos tienen que actualizar tres conectores distintos. Cuando añades un cuarto modelo, añades cuatro integraciones más. Cuando añades una quinta herramienta, añades tres integraciones más.

El diagrama de la izquierda en pantalla es esto: un grafo denso con flechas cruzando en todas direcciones. N modelos multiplicado por M herramientas. A escala organizacional, este grafo se vuelve inmanejable. No es un problema técnico puntual. Es deuda de integración que crece de forma exponencial con tu organización.

---

### Bloque 2 — La solución: N + M en lugar de N × M

Model Context Protocol, MCP, es un estándar abierto que convierte ese producto cartesiano en una suma.

El principio es el mismo que resolvió el problema de los drivers de impresora hace décadas. En lugar de que cada sistema operativo escriba un driver específico para cada impresora, defines un protocolo estándar: cualquier impresora que habla el protocolo funciona con cualquier sistema operativo que lo entiende. El número de integraciones pasa de N×M a N+M.

MCP hace lo mismo para modelos y herramientas. Define dos roles.

El primero es el cliente MCP. Los modelos — o más precisamente, las aplicaciones que orquestan llamadas a modelos — son clientes MCP. Hablan el protocolo estándar para descubrir qué herramientas hay disponibles y para llamarlas.

El segundo es el servidor MCP. Tus herramientas — tu base de datos, tu API interna, tu sistema de ficheros — se exponen como servidores MCP. Definen qué operaciones ofrecen, qué parámetros aceptan, qué devuelven.

El resultado es el diagrama de la derecha en pantalla: en lugar de un grafo denso, tienes dos grupos conectados a un bus central. A la izquierda, tus modelos. A la derecha, tus herramientas. Todos hablan el mismo protocolo. Cualquier modelo puede usar cualquier herramienta sin integración adicional.

Cuando añades un cuarto modelo, tiene acceso automático a todas las herramientas existentes. Cuando añades una quinta herramienta y la expones como servidor MCP, todos los modelos existentes pueden usarla. El trabajo marginal de añadir un nuevo participante es constante, no proporcional al número de participantes que ya existen.

---

### Bloque 3 — Cómo funciona en la práctica

El flujo concreto es el siguiente.

Un orquestador arranca con una lista de servidores MCP configurados. Puede ser un servidor que gestiona documentos, otro que accede a una base de datos, otro que llama a una API externa. El orquestador interroga a cada servidor: ¿qué herramientas ofreces? Cada servidor responde con un esquema: nombre de la herramienta, descripción, parámetros que acepta, tipo de resultado que devuelve.

Esas descripciones van al LLM. El LLM las recibe como parte de su contexto y sabe que puede usarlas. Cuando el LLM decide que necesita información de la base de datos, emite una llamada de herramienta: "llama a la función `buscar_cliente` con este parámetro". El orquestador intercepta esa llamada, la enruta al servidor MCP correcto, ejecuta la operación, y devuelve el resultado al LLM. El LLM continúa.

Desde el punto de vista del LLM, el mecanismo es idéntico a un function call normal. Lo que MCP aporta no es un mecanismo nuevo de llamada. Aporta la estandarización del protocolo de descubrimiento y comunicación. El servidor MCP puede vivir en el mismo proceso, en un proceso separado, o en una máquina remota. El protocolo de comunicación es el mismo en todos los casos.

Esto tiene una implicación de diseño importante: cuando cambias de modelo — de un proveedor a otro, de una versión a otra — tus servidores MCP no cambian. La herramienta no sabe ni le importa qué modelo está al otro lado. Solo habla el protocolo.

---

### Bloque 4 — Cuándo construir un servidor MCP propio

La pregunta que tienes que hacerte no es "¿debería usar MCP?". Es "¿cuántos agentes o modelos van a necesitar esta herramienta?".

Si la respuesta es más de uno, construir un servidor MCP es la decisión correcta. Tienes una herramienta interna — pongamos, acceso a vuestro sistema de CRM — y tres agentes distintos la necesitan. Sin MCP, son tres integraciones con tres variaciones de lógica. Con MCP, es un servidor que los tres usan igual. Un punto de mantenimiento. Un punto de autenticación. Un contrato de interfaz compartido.

Hay otros factores que también empujan hacia MCP. Si quieres estandarizar el acceso a tus sistemas internos y que distintos equipos puedan construir agentes sin tener que entender la implementación interna de cada herramienta, el servidor MCP es la capa de abstracción correcta. El equipo que mantiene la herramienta publica el servidor. Los equipos que construyen agentes lo consumen sin saber cómo está implementado por dentro.

También si quieres que tu integración sea agnóstica al modelo. Si hoy usas un modelo y en seis meses cambias a otro, un servidor MCP no requiere trabajo de migración. El nuevo modelo es cliente MCP, habla el mismo protocolo, y usa tus herramientas sin cambios.

Cuándo no construir un servidor MCP: cuando tienes una integración puntual para un único agente que no va a ser compartida. Si un solo pipeline necesita llamar a un endpoint específico una vez, la integración directa es más rápida de implementar y el overhead de levantar un servidor MCP no aporta valor. MCP es infraestructura de reutilización. Si no hay reutilización, es overhead.

---

### Decisión de diseño (cierre, ~1 min)

La regla es directa.

Si más de un agente o modelo va a necesitar la misma herramienta, construye un servidor MCP. No intentes optimizar la primera vez: si ves que tienes dos agentes que necesitan lo mismo, ese es el momento de estandarizar.

Si es una integración puntual para un solo agente, integración directa. No añadas capas que no aportan valor en ese contexto.

La señal de que necesitas MCP suele llegar cuando empiezas a copiar y pegar código de integración entre proyectos. Eso es el indicador de que la herramienta debería ser un servidor compartido.

El punto arquitectónico de fondo: tus herramientas internas expuestas como servidores MCP son reutilizables por cualquier modelo ahora y en el futuro. No estás atado a ningún proveedor. Cambias el modelo, el servidor MCP no se mueve. Esa es la apuesta de diseño que MCP te permite hacer.

## Spec del diagrama

**Tipo:** Excalidraw
**Elementos:**
- Dos paneles lado a lado con línea vertical divisoria
- Panel izquierdo (fondo rojo muy suave): título `"Sin MCP — N × M integraciones"`
  - Tres rectángulos a la izquierda con etiquetas: `"Modelo A"`, `"Modelo B"`, `"Modelo C"`
  - Cuatro rectángulos a la derecha con etiquetas: `"BD Clientes"`, `"Sistema Tickets"`, `"Almacén Docs"`, `"API Calendario"`
  - Flechas cruzadas entre todos los modelos y todas las herramientas (grafo denso, 12 flechas aproximadas)
  - Anotación inferior: `"3 modelos × 4 herramientas = 12 integraciones. Cada cambio impacta múltiples conectores."`
- Panel derecho (fondo verde muy suave): título `"Con MCP — N + M integraciones"`
  - Tres rectángulos a la izquierda con etiquetas: `"Modelo A (cliente MCP)"`, `"Modelo B (cliente MCP)"`, `"Modelo C (cliente MCP)"`
  - Rectángulo central grande: `"MCP — Protocolo estándar"` con borde destacado
  - Cuatro rectángulos a la derecha con etiquetas: `"BD Clientes (servidor MCP)"`, `"Sistema Tickets (servidor MCP)"`, `"Almacén Docs (servidor MCP)"`, `"API Calendario (servidor MCP)"`
  - Flechas de modelos al bus central, flechas del bus central a herramientas (7 flechas limpias)
  - Anotación inferior: `"3 + 4 = 7 integraciones. Añadir un modelo o herramienta cuesta 1 integración, no N."`
- Nota flotante en el panel derecho: `"Cambiar de modelo: 0 cambios en servidores MCP"` con icono de check

**Flujo visual:** Panel izquierdo aparece primero durante el Bloque 1. Panel derecho se revela durante el Bloque 2. Las flechas del panel izquierdo se añaden una a una para ilustrar el crecimiento. El panel derecho aparece completo como contraste visual.
