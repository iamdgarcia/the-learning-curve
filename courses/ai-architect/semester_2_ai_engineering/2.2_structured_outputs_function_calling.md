# Structured Outputs y Function Calling

**Semestre:** 2 — AI Engineering
**Lección:** 2.2
**Duración estimada:** 8-10 min
**Formato visual:** Excalidraw (dos flujos paralelos comparativos)

---

## Objetivo de la lección

Al terminar esta lección, el alumno diseña la capa de salida del LLM como una interfaz tipada que el resto del sistema puede consumir de forma fiable, en lugar de texto libre que hay que parsear.

---

## Guión

### Intro (25 seg)

En la lección anterior decidiste cuándo usar un LLM. Ahora asumes que lo vas a usar. La pregunta siguiente es: ¿cómo estructura el LLM su respuesta para que el resto de tu sistema pueda consumirla?

Esta es una de las decisiones más ignoradas en sistemas de IA en producción. Y es la que marca la diferencia entre un sistema que funciona en demos y uno que funciona en producción.

---

### Bloque 1 — El problema del texto libre

Mira el flujo de la izquierda en el diagrama. Esto es lo que pasa sin structured outputs.

Le preguntas al LLM el precio de un producto. Te devuelve: "El precio del producto es 42 euros, incluyendo IVA". Ahora tienes que parsear eso. Escribes un regex. Funciona para el ochenta por ciento de los casos.

El problema es el veinte por ciento restante. A veces el modelo responde "42,00 €". A veces "EUR 42". A veces "El precio es de cuarenta y dos euros". A veces añade un párrafo de contexto antes del número. A veces, en edge cases que no anticipaste, el modelo cambia el formato de respuesta porque el prompt llegó con una pequeña variación en el contexto.

Tu regex falla. Tu heurística falla. Tu sistema de producción lanza un error que no entiendes hasta que revisas el log y ves el output del modelo.

Esto no es un fallo del modelo. El modelo está haciendo exactamente lo que le pediste: responder la pregunta en lenguaje natural. El fallo es de diseño: estás usando el LLM como si fuera un sistema de texto libre y luego intentando convertir ese texto libre en datos estructurados. Eso es frágil por construcción.

---

### Bloque 2 — Structured outputs: el LLM como generador de JSON tipado

El flujo de la derecha en el diagrama. Structured outputs.

La idea es simple: en lugar de pedirle al LLM que responda en lenguaje natural y luego parsear esa respuesta, le dices exactamente qué schema de JSON debe producir. El modelo está obligado a seguirlo. No es una sugerencia. No es una convención. Es una restricción a nivel de inferencia: el modelo no puede devolver algo que no cumpla el schema.

El resultado es predecible. Si defines un schema con un campo "precio" de tipo número y un campo "incluye_iva" de tipo booleano, eso es exactamente lo que vas a recibir. Siempre. En cada llamada.

Esto cambia fundamentalmente cómo diseñas el downstream del LLM. En lugar de un parser frágil, tienes un objeto tipado. El resto del sistema consume ese objeto como consumiría cualquier objeto tipado: con acceso directo a los campos, sin parsing, sin regex, sin manejo de casos edge de formato.

El schema también documenta la interfaz. Cuando un compañero mira tu código, el schema le dice exactamente qué puede esperar del LLM. Es una interfaz igual que una función tipada es una interfaz.

---

### Bloque 3 — Function calling: el LLM decide qué herramienta usar

Function calling es un nivel más arriba. No solo defines el schema de la respuesta — defines funciones que el LLM puede llamar, y el LLM decide cuál llamar y con qué argumentos.

El flujo es este. Le dices al LLM: "Tienes estas herramientas disponibles: buscar en base de datos, enviar email, crear ticket". El usuario escribe "Crea un ticket urgente para el cliente García con el problema de facturación". El LLM interpreta eso y responde no con texto, sino con una llamada estructurada a la función "crear ticket" con los argumentos: cliente "García", prioridad "urgente", categoría "facturación".

Tu código recibe esa llamada estructurada, ejecuta la función real, obtiene el resultado, y puede devolver ese resultado al LLM para que continúe la conversación.

El LLM nunca ejecuta la función directamente. El LLM produce una instrucción estructurada que dice qué función llamar y con qué argumentos. Tu código ejecuta la función. Esto es crítico: el LLM no tiene acceso directo a tus sistemas. Tú controlas qué funciones existen, qué argumentos aceptan, y qué hace cada una.

Este patrón es la base de los agentes, que veremos en profundidad en el Semester 3. Por ahora, la arquitectura clave es: LLM como motor de decisión → función determinista como executor → resultado de vuelta al LLM si hace falta.

---

### Bloque 4 — Cómo encaja en la arquitectura del sistema

En el diagrama ves las dos capas marcadas con sus responsabilidades.

La capa del LLM tiene una sola responsabilidad: entender el input y producir una instrucción o dato estructurado. No ejecuta nada. No accede a nada directamente. Produce un output que cumple un schema.

La capa del sistema downstream tiene otra sola responsabilidad: consumir ese output tipado y actuar en consecuencia. No interpreta lenguaje natural. No parsea texto. Recibe un objeto con tipos garantizados y lo usa.

Entre las dos capas hay un contrato: el schema. Ese contrato es explícito, versionable, testeable. Puedes escribir tests unitarios que validen que el LLM cumple el schema en distintos casos. Puedes cambiar el modelo subyacente y verificar que el schema sigue cumpliéndose. Puedes versionar el schema igual que versionas una API.

Esta es la diferencia entre un sistema de IA que puedes mantener y uno que no.

---

### Bloque 5 — El antipatrón y la capa de validación

Aunque el modelo esté obligado a seguir el schema, añade validación en tu código.

Los modelos cometen errores en edge cases. Un campo que definiste como entero puede llegar como string en condiciones de contexto muy largas. Un enum que definiste con tres opciones puede tener un valor que no esperabas si el modelo confundió el schema de una versión anterior. Los proveedores actualizan los modelos y a veces el comportamiento cambia ligeramente.

La capa de validación del schema en tu código es barata de implementar y te salva de errores que de otra forma llegarían a producción silenciosamente.

En el diagrama, el error path está marcado en rojo en ambos flujos. En el flujo sin structured output, el error ocurre en el parse y es frecuente. En el flujo con structured output, el error ocurre en la validación del schema y debería ser raro, pero existe. La diferencia es que en el segundo caso tienes un lugar explícito donde detectarlo.

El antipatrón que quiero que recuerdes: parsear texto libre con regex en un sistema de producción. Funciona en la demo. Falla en producción. Siempre es así.

---

### Decisión de diseño (cierre, ~1 min)

La regla es simple: si tu código depende de la estructura del output del LLM, define un schema. Punto.

No "si el output es complejo". No "si el output va a una base de datos". Si tu código tiene que leer algún campo del output del LLM, ese output tiene que tener un schema definido y validado.

La pregunta que tienes que saber responder cuando diseñas cualquier componente con un LLM es: ¿qué contrato de datos define la salida de este LLM hacia el resto del sistema? Si no puedes responder esa pregunta con un schema concreto, el diseño está incompleto.

Cuándo usar function calling versus structured output simple: usa structured output cuando el LLM produce un dato o una respuesta que el sistema consume directamente. Usa function calling cuando el LLM necesita elegir entre múltiples acciones posibles o cuando el resultado de la acción tiene que volver al LLM para continuar el flujo.

Siguiente lección: una vez que tienes el output controlado, el problema siguiente es la memoria. Los LLMs no recuerdan nada entre llamadas por defecto. Cuatro patrones para resolver eso.
