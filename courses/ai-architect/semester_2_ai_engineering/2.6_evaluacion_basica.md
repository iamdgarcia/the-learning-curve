# Evaluación básica: cómo sabes si tu sistema funciona

**Semestre:** 2 — AI Engineering
**Lección:** 2.6
**Duración estimada:** 8-10 min
**Formato visual:** Excalidraw (pipeline con tres ramas de evaluación)

---

## Objetivo de la lección

Al terminar esta lección, el alumno define qué significa "funciona" para su sistema LLM, construye un golden dataset inicial, y sabe qué método de evaluación aplicar en cada contexto.

---

## Guión

### Intro (25 seg)

En un sistema de software tradicional sabes si funciona porque tienes tests. Ejecutas el código con una entrada, compruebas que el output es exactamente el que esperabas, y el test pasa o falla. Determinismo. Sin ambigüedad.

Un sistema LLM no funciona así. El mismo prompt puede producir respuestas distintas en distintas llamadas, todas igualmente correctas. No hay un output exacto que comparar. ¿Cómo testeas algo que por naturaleza no es determinista?

Esa es la pregunta que resuelve esta lección.

---

### Bloque 1 — El primer problema: definir qué significa "funciona"

Antes de evaluar nada, tienes que responder una pregunta que parece obvia pero que la mayoría de equipos no responde antes de empezar: ¿qué tiene que hacer bien tu sistema?

No a nivel de descripción general. A nivel concreto, medible. Para un sistema de soporte al cliente: ¿el output tiene que identificar correctamente la intención del usuario? ¿Tiene que sugerir una solución dentro de una lista de soluciones válidas? ¿Tiene que responder en menos de doscientas palabras? ¿No puede incluir información falsa sobre precios?

Cada una de esas es una dimensión de calidad diferente, con un método de evaluación diferente. Si no las defines antes de desplegar, no tienes forma de saber si el sistema las cumple.

El error que veo en muchos equipos es saltarse esta definición y ir directamente a "vamos a probarlo a mano". El problema es que "probarlo a mano" sin criterios explícitos no es evaluación. Es impresión subjetiva. Y las impresiones subjetivas no detectan regresiones, no escalan, y no dan confianza para desplegar.

El primer entregable de cualquier sistema LLM antes de producción no es el código. Es la definición de qué significa "funciona".

---

### Bloque 2 — El golden dataset

La herramienta que convierte esa definición en algo medible se llama golden dataset.

Un golden dataset es un conjunto de pares input-criterio: una entrada concreta y el resultado que el sistema debería producir — o las propiedades que ese resultado tiene que cumplir. No siempre es un output exacto. A veces es un conjunto de condiciones: el output tiene que mencionar estos temas, no tiene que mencionar estos otros, tiene que tener este formato, tiene que estar en este rango de longitud.

El golden dataset es el contrato de comportamiento de tu sistema. Si no lo tienes, no tienes forma de responder "¿funciona?" ni "¿ha dejado de funcionar?".

¿Cómo se construye? La primera versión viene de dos fuentes. La primera es el diseño: casos que representan los escenarios más importantes que el sistema tiene que manejar bien, incluyendo edge cases. La segunda son ejemplos reales de producción marcados por humanos — "esta respuesta es buena", "esta no cumple el criterio X".

El golden dataset no es estático. Crece. Cada vez que un bug llega a producción — una respuesta incorrecta, un comportamiento inesperado — ese caso de prueba entra al golden dataset. El dataset acumula la historia de los fallos que el sistema ha tenido. Con el tiempo, ejecutar el golden dataset completo es la forma más rápida de detectar si un cambio ha roto algo.

Esta práctica tiene un nombre en la ingeniería de software tradicional: test regression. La versión para sistemas LLM es el mismo principio aplicado a outputs no deterministas.

---

### Bloque 3 — Los tres enfoques de evaluación

Una vez tienes el golden dataset, necesitas ejecutarlo. Hay tres formas de hacerlo, con distintas capacidades, costes y velocidades.

El primero son las heurísticas programáticas. Son checks que puedes codificar directamente: ¿el output tiene más de cincuenta palabras? ¿Contiene los campos esperados si la salida es JSON? ¿No incluye palabras que están en tu lista de restricciones? ¿La respuesta empieza con el formato correcto?

Las ventajas son claras: velocidad máxima, coste mínimo, determinismo total. Puedes ejecutar estas heurísticas en cada llamada en producción con latencia despreciable. El límite es también claro: solo capturan dimensiones que puedes formalizar con reglas explícitas. No detectan si el tono es apropiado, si el razonamiento es correcto, si la respuesta realmente responde la pregunta.

El segundo enfoque es LLM-as-a-judge. En lugar de un humano o de una heurística, usas otro modelo de lenguaje para evaluar si el output cumple el criterio. Le das al juez el input original, el output generado, y el criterio de evaluación, y le pides que decida si el output es aceptable.

La potencia es mayor: el juez puede evaluar dimensiones que las heurísticas no pueden capturar — calidad del razonamiento, coherencia, completitud, adecuación del tono. El coste es más alto que las heurísticas. La velocidad es más baja. Y aparece una fuente de error nueva: el juez tiene sus propios sesgos, puede cometer errores, y sus decisiones son probabilísticas. Necesitas validar que el juez es un evaluador confiable para tu dominio específico, lo que requiere comparar sus veredictos con los de humanos en una muestra.

El tercero es la evaluación humana. Un revisor humano con conocimiento del dominio evalúa el output. Es la forma más lenta y cara de evaluar, y también la más fiable para criterios subjetivos o que requieren juicio de dominio. La evaluación humana no puede ejecutarse en cada llamada de producción. Pero es imprescindible para construir el golden dataset inicial y para calibrar el LLM-as-a-judge.

---

### Bloque 4 — Cuándo usar cada uno

El diagrama en pantalla muestra el pipeline completo: el output del sistema llega a tres ramas en paralelo.

La rama de heurísticas programáticas está siempre activa en producción. Checks continuos, baratos, rápidos. Son el primer filtro para detectar fallos evidentes.

La rama de LLM-as-a-judge se activa para evaluación de regresión: cuando cambias el modelo, el prompt, o cualquier componente del sistema, ejecutas el golden dataset completo con el juez y compruebas si el comportamiento ha cambiado. También puedes muestrear un porcentaje de llamadas de producción y evaluarlas con el juez para detectar degradación gradual.

La rama de evaluación humana se activa para construir o expandir el golden dataset, para validar que el juez está calibrado correctamente, y para casos donde el criterio de evaluación es ambiguo o muy específico del dominio.

La regla de cuándo necesitas humanos: si el criterio de evaluación es subjetivo o requiere juicio especializado — legal, médico, técnico muy específico — necesitas humanos al menos para validar que el criterio está bien definido y para calibrar el juez. Puedes delegar la ejecución en el juez una vez que confías en su calibración.

La anotación en el diagrama es importante: la evaluación humana tiene coste alto y velocidad baja. El LLM-as-a-judge tiene coste medio y velocidad media. Las heurísticas tienen coste bajo y velocidad alta. El sistema correcto combina las tres en los contextos correctos, no elige una y descarta las otras.

---

### Bloque 5 — El ciclo de vida del golden dataset

Un detalle final que separa los sistemas bien mantenidos de los que se degradan silenciosamente.

El golden dataset no termina cuando haces el despliegue inicial. Funciona en un ciclo: el sistema produce outputs en producción, algunos de esos outputs son incorrectos o subóptimos, esos casos se capturan y se añaden al golden dataset, el dataset crece, y la próxima vez que evalúas el sistema cubres más superficie.

La señal de entrada para añadir un caso al golden dataset puede ser explícita — un usuario reporta un problema — o implícita — el LLM-as-a-judge marca un output como problemático. Cualquiera de los dos es válida.

El resultado a largo plazo es un dataset que representa fielmente el espacio de comportamientos que importan en tu sistema específico. Eso es mucho más valioso que un dataset construido solo desde el diseño inicial, que inevitablemente no cubre los edge cases que aparecen en producción real.

---

### Decisión de diseño (cierre, ~1 min)

Dos preguntas para el cierre.

Primera: antes de desplegar, ¿tienes un golden dataset con al menos veinte casos que representen los escenarios más importantes y los edge cases conocidos? Si no, ese es el trabajo previo al despliegue que falta.

Segunda: cuando confías en LLM-as-a-judge como evaluador, ¿has validado que sus veredictos coinciden con los de humanos en una muestra representativa de tu dominio? Si no has hecho esa calibración, estás asumiendo que el juez es correcto sin evidencia.

La evaluación no es un paso que haces antes del despliegue y olvidas. Es un sistema que funciona en paralelo al sistema principal y que acumula conocimiento con el tiempo. Los sistemas LLM sin evaluación sistemática se degradan silenciosamente y sin aviso. Los que tienen evaluación sistemática muestran exactamente cuándo y en qué dimensión se degradan.

## Spec del diagrama

**Tipo:** Excalidraw
**Elementos:**
- Nodo de entrada arriba al centro: `"Sistema LLM"` con flecha saliente hacia abajo
- Nodo intermedio: `"Output generado"`
- Desde el nodo de output, tres flechas divergentes hacia tres ramas:
  - Rama izquierda — rectángulo con borde naranja: `"HEURÍSTICAS PROGRAMÁTICAS"` — contenido interior: `"Checks de formato / longitud / campos / palabras prohibidas"` — bajo el rectángulo dos etiquetas: `"Velocidad: ALTA"` y `"Coste: BAJO"`
  - Rama central — rectángulo con borde azul: `"LLM-AS-A-JUDGE"` — contenido interior: `"Otro modelo evalúa el output según el criterio"` — bajo el rectángulo dos etiquetas: `"Velocidad: MEDIA"` y `"Coste: MEDIO"` — nota adicional: `"Requiere calibración con humanos"`
  - Rama derecha — rectángulo con borde verde: `"EVALUACIÓN HUMANA"` — contenido interior: `"Revisión por expertos del dominio"` — bajo el rectángulo dos etiquetas: `"Velocidad: BAJA"` y `"Coste: ALTO"` — nota adicional: `"Imprescindible para el golden dataset inicial"`
- Las tres ramas convergen en un nodo inferior: `"MÉTRICAS — Calidad del sistema"`
- Del nodo de métricas, flecha hacia nodo final: `"DECISIÓN DE RELEASE"` con dos salidas: `"Desplegar"` y `"Iterar"`
- Caja flotante separada a la izquierda: `"GOLDEN DATASET"` con flecha punteada hacia el nodo de output indicando `"Casos de referencia para evaluación de regresión"` y flecha de retorno desde el nodo de decisión indicando `"Bugs en producción → añadir al dataset"`
- Anotación en el margen derecho con recuadro de aviso: `"Si el criterio requiere juicio de dominio, necesitas humanos para calibrar el juez antes de automatizar"`

**Flujo visual:** El nodo del Sistema LLM y el Output aparecen primero. Las tres ramas se revelan una a una durante el Bloque 3, de izquierda a derecha. El nodo de métricas y la decisión de release aparecen durante el Bloque 4. La caja del golden dataset aparece durante el Bloque 2 y el Bloque 5. La anotación de aviso aparece durante la Decisión de diseño.
