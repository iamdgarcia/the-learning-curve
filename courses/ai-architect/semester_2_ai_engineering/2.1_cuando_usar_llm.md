# Cuándo usar un LLM y cuándo código tradicional

**Semestre:** 2 — AI Engineering
**Lección:** 2.1
**Duración estimada:** 7-9 min
**Formato visual:** Excalidraw (árbol de decisión interactivo)

---

## Objetivo de la lección

Al terminar esta lección, el alumno puede tomar la decisión arquitectónica más ignorada en sistemas con IA: cuándo un LLM es la herramienta correcta y cuándo no lo es.

---

## Guión

### Intro (25 seg)

Arrancamos el Semester 2. Ya sabes cómo funciona un LLM por dentro. Ahora el trabajo es saber cuándo usarlo.

La decisión más importante en arquitectura de IA no es qué modelo elegir. No es cómo hacer el fine-tuning. Es esta: ¿necesito un LLM aquí o puedo resolverlo con código?

La mayoría de los equipos no se hacen esta pregunta. Y eso les cuesta dinero, tiempo de debugging y sistemas que fallan de formas que no anticiparon.

---

### Bloque 1 — En qué es bueno un LLM (y en qué no)

Empieza por el lado izquierdo del árbol en el diagrama. Esos son los casos donde un LLM gana.

Un LLM es bueno en comprensión de lenguaje natural. Si el input llega como texto no estructurado, ambiguo, en múltiples idiomas, con errores ortográficos, con sinónimos que significan lo mismo según el contexto — el LLM navega eso bien. El código tradicional no.

Un LLM es bueno en razonamiento difuso. Si la tarea requiere interpretar intención, no solo palabras exactas, el LLM tiene ventaja. Clasificar si un email es urgente, entender si una queja del usuario es técnica o de facturación, detectar si un fragmento de texto es relevante para una consulta aunque no comparta ni una palabra exacta.

Un LLM es bueno en generalización. Le puedes mostrar diez ejemplos y aplica el patrón a casos que no vio nunca. El código tradicional necesita que tú codifiques explícitamente cada caso.

Un LLM es bueno en síntesis. Tomar diez documentos y producir un resumen coherente es algo que el código no puede hacer sin un LLM.

Ahora el lado derecho del árbol. Código tradicional.

El código gana cuando necesitas exactitud al cien por cien. Calcular el precio de un pedido, validar un email, formatear una fecha, convertir una moneda. No hay "casi correcto" ahí. O es exacto o es un bug.

El código gana cuando la velocidad importa. Una consulta a base de datos por ID tarda microsegundos. Una llamada a un LLM tarda entre uno y cinco segundos. Si tienes un endpoint que se llama mil veces por segundo, eso no escala con un LLM.

El código gana a escala de coste. Una llamada a un LLM cuesta fracciones de céntimo por query. A diez millones de operaciones diarias, eso se convierte en miles de euros al mes. Si esa operación la podías hacer con un regex, estás pagando de más.

El código gana cuando necesitas reproducibilidad y auditoría. Dado el mismo input, el mismo código produce siempre el mismo output. Puedes reproducir exactamente lo que pasó el martes a las 14:32. Con un LLM, si no guardas el output, no puedes reconstruirlo.

---

### Bloque 2 — La trampa de "es más fácil de implementar"

En el diagrama, entre las dos columnas, hay una zona de peligro marcada. Esta es la trampa.

Usar un LLM para algo que podría hacer código es tentador porque la implementación inicial parece más simple. "Le pregunto al LLM y me devuelve lo que necesito". Sin lógica, sin regex, sin casos edge.

El problema aparece en producción.

Un LLM que valida emails te va a costar entre diez y cien veces más por operación que un regex. Y encima, va a fallar en casos edge que un regex no fallaría nunca: emails con caracteres unicode, dominios raros, formatos que el modelo no vio mucho en entrenamiento. Una función determinista es perfectamente predecible. El LLM no.

Cuando algo falla en producción y necesitas debuggear, el código tiene un stack trace claro. El LLM tiene un output que en esa llamada específica fue distinto por alguna razón que no puedes reconstruir si no guardaste el prompt completo y el output completo de esa invocación.

La heurística práctica es esta: si el input es lenguaje natural no estructurado, o si la tarea requiere comprensión de intención, considera el LLM. Si el input es estructurado y la respuesta tiene que ser exacta, usa código. Siempre.

---

### Bloque 3 — El caso híbrido: LLM decide, código ejecuta

La parte más interesante del árbol es el nodo central: "Híbrido".

Este patrón es el más potente y el más subestimado. El LLM actúa como cerebro: entiende la intención del usuario, decide qué hacer, produce una instrucción estructurada. El código ejecuta esa instrucción de forma determinista.

Ejemplo concreto. Un usuario escribe: "Muéstrame las facturas de los últimos tres meses del cliente García". El LLM interpreta eso, entiende que hay un nombre de cliente y un rango de fechas, y produce una instrucción estructurada: cliente "García", fecha inicio primero de abril, fecha fin treinta de junio. Tu código toma esa instrucción y ejecuta la consulta a la base de datos exactamente como lo haría siempre. La base de datos devuelve el resultado. El LLM puede entonces formatear la respuesta de vuelta al usuario.

El LLM nunca toca la base de datos directamente. El código nunca interpreta lenguaje natural directamente. Cada uno hace lo que hace bien.

Esto es lo que se llama function calling o tool use, y es el tema de la Lección 2.6. Por ahora quédate con el patrón: el LLM como interfaz de lenguaje natural sobre sistemas deterministas.

---

### Bloque 4 — Ejemplos concretos para cada nodo del árbol

Completa el árbol con los ejemplos del diagrama.

LLM puro: clasificar la intención de un mensaje de soporte, resumir un documento de cincuenta páginas, extraer entidades de un formulario en texto libre, detectar el idioma de un texto, generar variantes de copy.

Código puro: validar el formato de un email, calcular el total de una factura con descuentos e impuestos, ordenar una lista de resultados por fecha, consultar un registro por ID, comprobar si un usuario tiene permisos.

Híbrido: buscador en lenguaje natural sobre una base de datos estructurada, asistente que puede ejecutar acciones en el sistema, procesamiento de formularios en texto libre que termina escribiendo a una base de datos relacional, sistema de soporte que entiende la queja y luego llama a la API de CRM.

---

### Decisión de diseño (cierre, ~1 min)

El árbol de decisión que tienes en pantalla tiene tres preguntas.

Primera: ¿El input es lenguaje natural no estructurado o requiere comprensión de intención? Si no, usa código.

Segunda: ¿El output necesita ser correcto al cien por cien, reproducible, o auditable de forma exacta? Si sí, usa código.

Tercera: ¿El volumen de operaciones hace el coste de un LLM prohibitivo? Si sí, usa código.

Si superaste las tres preguntas — el input es lenguaje natural, el output puede tener cierta variabilidad, el volumen lo permite — entonces considera un LLM o un sistema híbrido.

La pregunta adicional para el híbrido: ¿Hay partes de la tarea que deben ser exactas? Si sí, aísla esas partes en código y que el LLM solo maneje la interpretación.

Un pipeline que usa LLM donde podría usar código es entre diez y cien veces más caro por operación, un orden de magnitud más lento, y significativamente más difícil de debuggear. La decisión de cuándo no usar un LLM es tan importante como la decisión de cuándo usarlo.

Siguiente lección: una vez que decides usar un LLM, cómo estructuras su output para que el resto del sistema pueda consumirlo de forma fiable.

## Spec del diagrama

**Tipo:** Excalidraw
**Elementos:**
- Nodo inicial arriba al centro: `"Problema a resolver"` con flecha hacia abajo
- Primera bifurcación (rombo de decisión): `"¿El input es lenguaje natural o requiere interpretar intención?"` — rama izquierda etiquetada `"No"` apunta a segunda decisión izquierda; rama derecha etiquetada `"Sí"` continúa bajando
- Segunda bifurcación izquierda (rombo): `"¿Necesita exactitud 100%, reproducibilidad o auditoría exacta?"` — rama `"Sí"` apunta a hoja `CÓDIGO`; rama `"No"` apunta a tercera bifurcación
- Tercera bifurcación (rombo): `"¿El volumen hace el coste de LLM prohibitivo?"` — rama `"Sí"` apunta a hoja `CÓDIGO`; rama `"No"` apunta a nodo `EVALUAR LLM`
- Nodo `EVALUAR LLM` con bifurcación adicional: `"¿Hay partes de la respuesta que deben ser exactas?"` — rama `"Sí"` apunta a hoja `HÍBRIDO`; rama `"No"` apunta a hoja `LLM`
- Hoja izquierda grande: caja `CÓDIGO` con color verde, interior: `"Validar email / Calcular precio / Ordenar lista / Consultar por ID"`
- Hoja derecha: caja `LLM` con color azul, interior: `"Clasificar intención / Resumir documento / Extraer entidades / Generar texto"`
- Hoja central: caja `HÍBRIDO` con color naranja, interior: `"LLM interpreta → código ejecuta"` y nota: `"Búsqueda en lenguaje natural / Asistentes con acciones / Formularios → base de datos"`
- Zona sombreada en rojo entre las columnas LLM y CÓDIGO: `"ZONA DE PELIGRO: usar LLM donde podría ir código = 10-100x más caro, más lento, más difícil de debuggear"`
- Anotación lateral derecha: `"Coste: microsegundos vs. segundos"` y `"Exactitud: 100% vs. probabilística"`

**Flujo visual:** El árbol se construye de arriba hacia abajo, apareciendo cada nodo de decisión mientras el presentador formula la pregunta correspondiente. Las hojas aparecen al llegar al Bloque 4. La zona de peligro aparece durante el Bloque 2.
